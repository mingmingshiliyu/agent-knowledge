1. 数据库整体设计思路
  - 我们的业务数据主要在 Go 侧用 GORM 操作 MySQL，Python 侧也有少量数据读写，整体设计遵循以下原则：
  - 按业务域分表：会话表、消息表、客户表、跟进记录表、质检报告表、Skill 配置表、评测用例表、审计日志表、系统配置表，每个表职责单一，避免大宽表。
  - 多租户隔离设计：所有业务表都带 tenant_id（律所ID）字段，按租户隔离数据，这是多租户 SaaS 的基础设计。
  - 软删除：业务表都用 deleted_at 软删除，不物理删除，保证数据可追溯，符合律所数据安全要求。
  - 审计字段：所有表带 created_at、updated_at、created_by、updated_by，记录数据变更时间和操作人，满足审计要求。
  - 冷热数据分离：历史会话、历史质检报告等冷数据，定期归档到历史表或低成本存储，主表只保留近期热数据，控制单表数据量，保证查询性能。
2. 核心表设计举例
  - 会话表（sessions）：id、tenant_id、user_id、session_type（咨询/质检/合同审查）、status（进行中/已结束/人工接管）、intent_tag（意向标签）、summary（会话摘要）、started_at、ended_at、created_at、updated_at、deleted_at。
    - 索引：tenant_id + user_id 联合索引、tenant_id + status 联合索引、tenant_id + created_at 联合索引，按租户和常用查询条件建索引。
  - 消息表（messages）：id、session_id、tenant_id、role（user/assistant/system）、content、token_count、cost、tool_calls（调用的工具记录，JSON）、created_at。
    - 索引：session_id + created_at 联合索引（按会话查消息，按时间排序）、tenant_id + created_at 索引。
    - 设计考虑：消息表数据量大，按 session_id 查询是主要场景，索引命中后速度快；content 是大文本，不建索引，需要全文检索的场景用 ES 或专门的检索服务。
  - 客户表（customers）：id、tenant_id、name、phone、email、source（来源渠道）、intent_level（高/中/低意向）、tags（标签，JSON）、latest_contact_at、created_at、updated_at。
    - 索引：tenant_id + phone 唯一索引（同租户下手机号唯一）、tenant_id + intent_level 索引、tenant_id + latest_contact_at 索引。
  - 审计日志表（llm_audit_logs）：id、tenant_id、session_id、skill_name、model_name、input_tokens、output_tokens、embedding_tokens、input_price_snapshot、output_price_snapshot、estimated_cost、status、error_msg、duration_ms、created_at。
    - 索引：tenant_id + created_at 联合索引、skill_name + created_at 索引、session_id 索引。
    - 设计考虑：这张表是成本分析的核心，按租户、时间、Skill 维度查询多，索引对应设计；数据量大，按月分表或归档。
  - 评测用例表（evaluation_cases）：id、skill_name、version、input（JSON）、expected_output（JSON）、assertions（JSON，断言配置）、category、created_at、updated_at。
    - 索引：skill_name + version 联合索引。
3. 索引优化实践
  - 原则一：联合索引优先，最左前缀匹配
    - 我们的查询几乎都带 tenant_id，所以联合索引都以 tenant_id 开头，比如 tenant_id + created_at、tenant_id + status，先按租户过滤掉大部分数据，再按其他条件过滤，效率高。
    - 避免建太多单列索引，联合索引能覆盖更多查询场景，一个 tenant_id + created_at 能满足"查某租户某时间段数据"和"查某租户所有数据按时间排序"两个场景。
  - 原则二：覆盖索引减少回表
    - 对于高频查询，尽量让索引覆盖查询字段，不用回表。比如会话列表查询只需要 id、status、intent_tag、started_at，就建 tenant_id + created_at + status + intent_tag 覆盖索引，直接从索引取数据，速度快。
  - 原则三：避免索引失效的写法
    - 不在索引字段上用函数、计算、隐式类型转换，比如 WHERE DATE(created_at) = '2024-01-01' 会导致 created_at 索引失效，改成范围查询 WHERE created_at >= '2024-01-01' AND created_at < '2024-01-02'。
    - 模糊查询避免左通配 %keyword，用右通配 keyword% 才能用到索引，需要全文检索的用 ES。
    - OR 条件两边都要有索引，否则会全表扫描，复杂查询改成 UNION。
  - 原则四：定期分析慢查询，针对性优化
    - 开启 MySQL 慢查询日志，定期用 pt-query-digest 分析，找出慢 SQL，用 EXPLAIN 看执行计划，判断是索引没命中、回表多、还是扫描行数多，针对性加索引或改写 SQL。
    - 我们有过一次消息表查询慢，EXPLAIN 发现用了 filesort，因为排序字段没在联合索引里，调整索引顺序后解决。
  - 原则五：控制索引数量
    - 不是索引越多越好，每个索引都增加写入开销，我们单表索引控制在 5 个以内，定期清理无用、重复索引，写入多的表尤其注意。
4. 查询优化实践
  - 分页优化：避免深度分页 LIMIT 100000, 20，越往后越慢，改成"上一页最后一条 ID + WHERE id < last_id LIMIT 20"的游标分页，或者用延迟关联，先查 ID 再回表，大幅提升深分页性能。
  - 批量操作：批量插入、批量更新用一条 SQL，不要循环单条，减少数据库交互次数，比如批量写审计日志，一次插几百条，性能提升几十倍。
  - 只查需要的字段：避免 SELECT *，只查业务需要的字段，减少数据传输和内存占用，也更容易命中覆盖索引。
  - 事务控制：事务尽量短小，不要在事务里做外部调用（调大模型、HTTP 请求），避免长事务占用连接和锁，导致并发问题。我们有过一次在事务里调外部接口，事务持有锁时间过长，导致其他请求阻塞，后来把外部调用移到事务外。
  - 连接池配置：GORM 配置数据库连接池，设置最大空闲连接、最大打开连接、连接最大生命周期，避免连接泄漏和频繁创建连接，根据并发量调整参数。
5. GORM 在项目中的使用实践
  - 基本用法：
    - 用 GORM 的 Model 定义表结构，tag 标注字段名、类型、索引、注释，自动迁移表结构（开发环境用 AutoMigrate，生产环境用 SQL 脚本变更，更可控）。
    - 链式调用做查询：db.Where("tenant_id = ? AND status = ?", tenantID, status).Order("created_at desc").Find(&sessions)，代码简洁可读。
    - 预加载（Preload）处理关联查询，避免 N+1 问题，比如查会话同时预加载消息，用 db.Preload("Messages").Find(&sessions)，一次查询搞定，不用循环查每条会话的消息。
  - 多租户自动隔离（核心实践）：
    - 这是我们 GORM 使用最有特色的部分，用 GORM 的插件（Callbacks）实现 tenant_id 自动注入和过滤，开发不用手动写，避免漏写导致跨租户数据泄露。
    - 实现方式：
      1. 注册 GORM 的 Query 回调，在查询执行前，自动从 context 中取出当前 tenant_id，拼接 WHERE tenant_id = ? 条件，所有查询自动带租户过滤。
      2. 注册 Create 回调，写入前自动从 context 取 tenant_id，赋值到模型的 TenantID 字段，开发不用手动设。
      3. Update、Delete 回调同样自动加 tenant_id 条件，防止越权修改删除其他租户数据。
    - 好处：开发只关心业务逻辑，租户隔离由框架自动保证，不会因为有人漏写 WHERE tenant_id 导致数据安全事故，这在多租户 SaaS 里是生命线。
    - 注意：超级管理员需要跨租户操作时，提供一个 SkipTenant() 方法，显式跳过租户过滤，并且记录审计日志，防止滥用。
  - 软删除支持：
    - GORM 原生支持软删除，模型里嵌入 gorm.DeletedAt，查询自动过滤已删除数据，删除操作自动变成 UPDATE deleted_at，不用自己写，符合我们的数据可追溯要求。
    - 需要查已删除数据时用 Unscoped()，显式查询，日常查询不会误删数据。
  - 事务处理：
    - 用 db.Transaction(func(tx *gorm.DB) error { ... }) 做事务，自动提交回滚，代码简洁，不用手动管理事务对象。
    - 事务里的操作用 tx 而不是 db，确保在同一个事务连接里，这个新手容易错，我们做了 code review 规范。
  - SQL 日志和慢查询：
    - 开发环境开启 GORM SQL 日志，打印每条 SQL 和执行时间，方便排查慢查询和索引问题。
    - 生产环境只打印慢 SQL（超过阈值的），配合 MySQL 慢查询日志，定位性能问题。
  - GORM 的不足和应对：
    - 复杂查询（多表联查、子查询、聚合统计）用 GORM 链式写起来别扭，也容易出问题，我们的应对是：复杂查询直接写原生 SQL，用 db.Raw(sql).Scan(&result)，简单 CRUD 用 GORM，扬长避短，不强行所有查询都用 ORM。
    - N+1 问题要注意，关联查询必须用 Preload，我们 code review 会检查循环里查数据库的代码，发现 N+1 及时优化。
    - 批量更新删除注意加条件，防止误操作全表，我们要求更新删除操作必须有 WHERE 条件，并且 review 确认。
6. Python 侧的数据库访问
  - Python 侧主要是 AI 服务，数据库操作不多，主要是读写会话状态、评测数据，用 SQLAlchemy（异步版 async-sqlalchemy）或直接用异步驱动，保持和 Go 侧一致的表结构和租户隔离逻辑。
  - 复杂的业务数据操作都在 Go 侧完成，Python 侧只做简单的 AI 相关数据读写，职责清晰，避免两边都写复杂业务逻辑导致不一致。
7. 落地效果和经验总结
  - 通过合理的表设计、索引优化和查询优化，核心接口查询响应时间都在 50ms 以内，即使数据量增长也保持稳定。
  - GORM 多租户自动隔离插件上线后，从未出现过跨租户数据泄露的安全事故，开发效率也提升了，不用每次都手动写 tenant_id 条件。
  - 慢查询治理后，数据库 CPU 使用率下降明显，高峰期也很平稳，没有出现过数据库性能瓶颈导致的服务不可用。
  - 经验总结：
    1. 数据库设计先想清楚查询场景，再建表建索引，索引是为查询服务的，不是拍脑袋建的。
    2. 多租户场景，租户隔离一定要用框架自动保证，不能靠人自觉，这是安全底线。
    3. ORM 用在简单 CRUD 提升效率，复杂查询用原生 SQL 可控性更好，不要为了用 ORM 而用 ORM。
    4. 慢查询治理是长期工作，定期分析优化，不要等出问题了才管。
    5. 控制单表数据量，冷热分离、分表归档，数据量太大时什么索引都不好使。

第25题：你们的 Redis 缓存是怎么用的？解决了哪些问题？
回答思路： 结合律所 AI 平台的具体场景，讲 Redis 的多种用途（会话缓存、高频问答缓存、分布式锁、限流、降级存储），以及缓存问题的处理，体现你对 Redis 多种数据结构和应用场景的熟练掌握。
参考答案：
1. Redis 在项目中的整体定位
  - Redis 是我们架构中非常核心的组件，不只是简单的缓存，而是承担了多种角色：热数据缓存、会话状态存储、分布式锁、限流、降级向量存储、消息队列（轻量场景），是 Go 和 Python 两侧都重度使用的基础设施。
  - 选型原因：性能高（毫秒级响应）、数据结构丰富（String/Hash/List/Set/ZSet）、支持持久化、生态成熟，AI 服务的很多场景都能完美适配。
2. 场景一：会话状态与热数据缓存（最核心）
  - 为什么需要：多轮咨询 Agent 的会话状态（历史消息、用户信息、已确认实体、当前意图、召回结果）需要高频读写，如果每次都查 MySQL，性能差且数据库压力大，而且会话是典型的热数据，活跃期间读写频繁。
  - 具体实现：
    - 用 Hash 结构存储会话状态，Key 设计为 session:{tenant_id}:{session_id}，Field 是状态字段（history、user_profile、confirmed_info、current_intent、retrieved_docs），Value 是序列化后的 JSON。
    - 会话创建时写入 Redis，每轮对话更新对应字段，会话结束后持久化到 MySQL，同时 Redis 保留一段时间（比如 7 天），用户短期内回来还能继续。
    - 设置过期时间（TTL），活跃会话访问时自动续期，长时间不活跃的会话自动过期，节省内存。
    - 历史消息用 List 结构，按时间顺序追加，分页读取方便，也方便截断滑动窗口。
  - 效果：会话状态读写从 MySQL 的几十毫秒降到 Redis 的 1-2 毫秒，接口响应速度大幅提升，同时 MySQL 压力减少 60% 以上。
  - 注意：Redis 里的会话数据是热数据，MySQL 是持久化备份，会话结束时必须异步落库，防止 Redis 重启丢失，我们有定时任务检查未落库的会话兜底。
3. 场景二：高频法律问答缓存（降本提速）
  - 为什么需要：很多用户问的法律问题是重复的（比如"离婚需要什么材料"、"劳动仲裁时效多久"、"欠钱不还怎么办"），每次都走 RAG 检索 + 大模型生成，既慢又费钱，这些高频问题答案相对固定，完全可以缓存。
  - 具体实现：
    - 用 String 结构，Key 设计为 faq:{tenant_id}:{question_hash}，question_hash 是用户问题的语义哈希（不是简单 MD5，而是先做归一化处理——去掉语气词、同义词替换、提取核心问题，再 hash，或者用 Embedding 向量做相似度匹配），Value 是缓存的答案 + 引用来源 + 元数据。
    - 用户提问先查缓存，命中（语义相似度超过阈值）直接返回，不用走检索和大模型；未命中才走完整 RAG 流程，生成答案后异步写入缓存。
    - 缓存的答案经过人工审核，确保质量，不是随便什么回答都缓存。
    - 设置合理的 TTL（比如 7-30 天），法律知识更新时主动失效对应缓存，避免答案过时。
    - 不同租户的缓存隔离，Key 带 tenant_id，A 律所的答案不会被 B 律所读到。
  - 效果：约 20-30% 的常见问题命中缓存直接返回，这部分请求响应从秒级降到毫秒级，同时节省了大模型调用成本，整体 Token 消耗降了约 15%。
  - 难点和应对：语义匹配缓存比精确匹配难，我们的做法是高频问题先做归一化提取核心意图，再做精确匹配，覆盖大部分重复问题；更复杂的语义相似缓存用向量相似度，但有一定误判风险，只对高置信度的命中直接返回，低置信度还是走完整流程。
4. 场景三：分布式锁（并发控制）
  - 为什么需要：分布式部署的服务，有些操作需要全局互斥，比如同一会话的并发请求处理、定时任务执行、缓存击穿保护、知识库更新锁，不用分布式锁会导致数据错乱或重复执行。
  - 具体实现：
    - 用 Redis 的 SET key value NX EX timeout 实现分布式锁，Key 是锁的标识，Value 是唯一请求 ID（防止误删别人的锁），NX 保证只有一个客户端能设置成功，EX 设置过期时间防止死锁。
    - 释放锁时用 Lua 脚本原子操作：先判断锁的 Value 是不是自己的，是才删除，防止锁过期后被别人获取，自己又误删了别人的锁。
    - 典型应用场景：
      1. 会话并发锁：同一个 session_id 的请求加锁，串行处理，防止用户快速连发两条消息导致会话状态读写冲突，锁粒度细（按会话），不影响其他会话。
      2. 缓存击穿保护：热点缓存失效时，只有一个请求去回源查数据库/大模型，其他请求等待或返回旧值，防止大量请求同时打到底层。
      3. 定时任务锁：多实例部署时，定时任务（比如会话归档、成本统计）只执行一次，用分布式锁抢执行权，避免重复执行。
      4. 知识库更新锁：同一个租户的知识库更新加锁，防止同时更新导致索引错乱。
  - 注意的坑：
    - 锁必须有过期时间，防止客户端宕机导致死锁。
    - 释放锁必须判断归属，不能乱删，用 Lua 脚本保证原子性。
    - 锁的粒度要合适，不能太粗（比如全局锁导致所有请求串行），也不能太细（锁太多管理复杂）。
    - 加锁操作要有超时和重试，不能一直等锁。
5. 场景四：限流（保护系统和成本）
  - 为什么需要：AI 服务调用大模型是要钱的，而且下游服务有承载上限，必须做限流，防止恶意刷接口、单用户过量调用、突发流量把系统打挂或导致成本暴增。
  - 具体实现：
    - 用 Redis + Lua 脚本实现滑动窗口限流，原子性好，精度高。
    - 多维度限流：
      1. 用户级限流：每个用户每分钟/每天最多调用多少次，防止单个用户刷量。
      2. 租户级限流：每个律所租户有整体调用配额和并发上限，防止一个租户占满所有资源，影响其他租户。
      3. 接口级限流：不同接口限流阈值不同，比如问答接口和质检接口限流不一样。
      4. 大模型调用限流：保护下游大模型 API，不超过服务商的限流阈值，也控制成本。
    - 限流策略：超过阈值返回 429 错误，提示"请求过于频繁，请稍后再试"，重要接口可以排队而不是直接拒绝。
    - 用 ZSet 实现滑动窗口：每个限流维度一个 ZSet，Key 是 rate:{dim}:{id}，Score 是请求时间戳，Member 是请求唯一 ID，每次请求先移除窗口外的旧请求，再统计窗口内请求数，超过阈值就拒绝，否则加入当前请求。
  - 效果：上线后成功拦截了几次恶意刷接口的情况，也避免了突发流量把大模型 API 打挂，成本也可控，没有出现过单日成本超预期的情况。
6. 场景五：降级用本地向量库存储（RAG 多级降级的关键）
  - 为什么需要：我们的 RAG 多级降级机制中，第二级是本地向量库，当远程 Embedding 服务不可用时，需要用本地预计算的向量做检索，Redis 作为轻量向量存储很合适。
  - 具体实现：
    - 法律 FAQ 的向量提前用 Embedding 模型计算好，存在 Redis 的 Hash 或专门的向量结构里，Key 是 vec:{tenant_id}:{doc_id}，Value 是序列化的向量数组 + 原文内容。
    - 远程服务不可用时，降级到本地，用 NumPy 在内存中计算查询向量和本地向量的余弦相似度，做 Top-K 召回，虽然数据量和更新频率不如远程，但核心 FAQ 都有，能保证基本问答能力。
    - 向量数据定期同步更新，和远程知识库保持基本一致。
  - 效果：这是我们多级降级机制的重要一环，远程服务故障时，本地向量库能覆盖大部分常见问题，问答功能基本可用，用户几乎感知不到故障，只是非常新的知识可能没有。
  - 为什么不用专门的向量数据库：降级场景是轻量的，数据量不大（几万条 FAQ），Redis + NumPy 完全够用，不用额外部署 Milvus 等重型向量库，节省运维成本，而且 Redis 已经是我们的基础组件，不用引入新依赖。
7. 场景六：轻量消息队列与异步任务
  - 为什么需要：有些轻量异步任务（比如写审计日志、更新统计、发送通知）不需要引入 Kafka/RabbitMQ 这么重的消息队列，用 Redis 的 List 或 Stream 做轻量队列足够。
  - 具体实现：
    - 用 List 实现简单的生产者消费者模式：LPUSH 生产任务，BRPOP 消费任务，支持阻塞等待，实现简单。
    - 用 Redis Stream 实现更可靠的消息队列，支持消息 ID、消费组、确认机制、消息回溯，适合需要可靠投递的场景。
    - 应用场景：审计日志异步写入、会话结束后异步生成跟进记录、质检完成后异步通知、缓存更新通知。
    - 注意：Redis 做队列适合轻量、允许少量丢失的场景，重要任务还是用专业消息队列（我们重要任务用 Celery + Redis，更可靠）。
8. 缓存常见问题的处理
  - 缓存穿透：查询不存在的数据，每次都打到底层。处理：1. 参数校验，非法请求直接拦截；2. 空结果缓存，短 TTL；3. 布隆过滤器（Bloom Filter）预判，不存在的直接返回，我们用 Redis 的布隆过滤器插件实现。
  - 缓存击穿：热点 key 过期，大量请求同时打到底层。处理：1. 分布式锁，只有一个请求回源；2. 热点数据永不过期，后台异步更新；3. 我们的高频问答缓存用了永不过期 + 主动更新的策略，法律知识更新时主动失效。
  - 缓存雪崩：大量 key 同时过期，或 Redis 故障。处理：1. 过期时间加随机偏移，打散失效时间；2. Redis 集群高可用，主从 + 哨兵；3. 服务降级，Redis 故障时走底层服务或降级逻辑，保证核心可用；4. 多级缓存，本地缓存（Caffeine/Go 的 sync.Map）+ Redis，即使 Redis 挂了，本地缓存还能顶一部分。
  - 缓存一致性：数据库更新后缓存怎么处理。我们的策略是"先更数据库，再删缓存"，而不是更新缓存，因为删缓存更简单，下次查询自动回源更新；重要数据更新后主动删对应缓存，同时有 TTL 兜底，最终一致；对于强一致要求的场景（比如用户余额），不用缓存，直接查数据库。
9. Redis 运维和监控
  - 部署模式：我们用 Redis 主从 + 哨兵模式，保证高可用，数据持久化用 RDB + AOF 混合模式，兼顾性能和数据安全。
  - 监控：用 Prometheus + Grafana 监控 Redis 的内存使用率、命中率、连接数、QPS、慢查询、主从同步状态，设置告警阈值，内存使用率超过 80%、命中率低于 90% 都告警。
  - 内存管理：设置最大内存，淘汰策略用 allkeys-lru（优先淘汰最近最少使用的 key），定期清理过期和无用的 key，防止内存打满。
  - 大 key 治理：定期扫描大 key（比如存了太多字段的 Hash、太大的 String），拆分或优化，大 key 会导致 Redis 阻塞，我们有过一次会话历史存太大导致查询慢，后来做了拆分。
10. 落地效果和经验总结
  - Redis 多场景应用后，整体接口响应速度提升明显，核心热数据查询从几十毫秒降到 1-2 毫秒，数据库和大模型的压力都大幅降低，成本也省了不少。
  - 多级降级机制因为有 Redis 本地向量库，远程服务故障时系统依然可用，可用性从 99.5% 提升到 99.9%。
  - 分布式锁和限流保证了并发安全和成本可控，没有出现过数据错乱或成本暴增的情况。
  - 经验总结：
    1. Redis 不只是缓存，要根据场景用合适的数据结构和功能，能解决很多问题，避免引入更多重型组件。
    2. 缓存三大问题（穿透、击穿、雪崩）必须提前考虑方案，不要等出问题了才处理。
    3. 缓存一致性要根据业务要求选择策略，强一致不用缓存，最终一致用"更库删缓存"。
    4. Redis 也要监控和运维，内存、命中率、大 key 都是重点，不要觉得 Redis 性能高就不管。
    5. 不要什么都放 Redis，冷数据、大对象、强一致数据不适合放缓存，合理选择才能发挥 Redis 的价值。

第26题：你们的 Docker Compose 是怎么编排服务的？CI/CD 流程是怎样的？
回答思路： 结合 Go + Python 混合架构的特点，讲 Docker Compose 的多服务编排、环境配置、依赖管理，再讲 CI/CD 流水线的完整流程，重点突出评测 Harness 作为质量门禁的特色，体现你对容器化和 DevOps 的实战经验。
参考答案：
1. Docker Compose 服务编排设计
  - 我们的开发和测试环境用 Docker Compose 编排所有服务，一键启动整个平台，降低开发环境搭建成本，也保证环境一致性；生产环境用 K8s，但 Compose 的服务划分和镜像构建是通用的。
  - 整体架构的服务划分：
services:
  # Go 侧服务
  gateway:          # API 网关 + Harness 运行时治理（Go + Gin/Hertz）
  skill-runner:     # Skill 执行调度服务（Go）
  # Python 侧 AI 服务
  rag-service:      # 法律问答 RAG 服务（Python + FastAPI）
  agent-service:    # 多轮咨询 Agent 编排服务（Python + FastAPI + LangGraph）
  asr-service:      # ASR 转写 + 质检服务（Python + FastAPI）
  evaluation-worker: # 评测 Harness 执行器（Python + Pytest）
  # 基础设施
  mysql:            # 业务数据库
  redis:            # 缓存 + 会话 + 分布式锁 + 限流
  # 可选服务（按需启动）
  milvus:           # 向量数据库（生产用，开发环境可用降级方案）
  etcd:             # 服务发现（可选）
  - 镜像构建优化：
    - Go 服务：多阶段构建，第一阶段用 golang 镜像编译，第二阶段用 alpine 或 distroless 镜像运行，最终镜像只有几十 MB，启动快、攻击面小。
    - Python 服务：多阶段构建，第一阶段用 python:slim 安装依赖（用 requirements.txt 或 poetry.lock 锁定版本），第二阶段精简运行时镜像，安装必要的系统依赖（比如 FFmpeg 用于音频处理），控制镜像大小；Python 镜像相对大，尽量精简，不用的依赖不装。
    - 依赖层缓存：把依赖安装（go mod download、pip install）放在代码拷贝之前，利用 Docker 层缓存，代码变更不用重新装依赖，构建速度快很多。
  - 环境配置管理：
    - 用 .env 文件管理环境变量（数据库密码、API Key、模型配置、端口等），不同环境（开发/测试/生产）用不同的 .env 文件，不提交到代码库，用示例文件 .env.example 说明需要哪些变量。
    - 敏感信息（大模型 API Key、数据库密码）不硬编码在镜像里，通过环境变量注入，生产环境用密钥管理服务。
    - Compose 里用 environment 或 env_file 引用变量，服务间通过服务名通信（比如 Python 服务连 MySQL 用 mysql:3306，Docker 内部 DNS 自动解析）。
  - 依赖和启动顺序控制：
    - 用 depends_on 声明服务依赖，比如 AI 服务依赖 MySQL 和 Redis，先启动基础设施再启动应用服务。
    - 注意 depends_on 只保证启动顺序，不保证服务就绪，所以应用服务里做了健康检查和重试逻辑——连不上数据库就重试等待，不会直接崩溃，这是分布式系统的基本容错。
    - 基础设施服务（MySQL、Redis）配置健康检查（healthcheck），应用服务等待依赖健康后再启动。
  - 端口和网络管理：
    - 只有网关服务暴露端口到宿主机，其他内部服务不暴露端口，只在 Docker 内部网络通信，减少攻击面，也避免端口冲突。
    - 用自定义 bridge 网络，服务间通过服务名访问，网络隔离，不同项目的 Compose 网络不互通。
  - 数据持久化：
    - MySQL、Redis 用 volumes 挂载数据卷，容器删除重建数据不丢失。
    - 开发环境可以用 bind mount 挂载代码目录，配合热重载（Go 的 air、Python 的 uvicorn --reload），改代码不用重新构建镜像，开发体验好。
  - 按需启动：
    - 用 profiles 区分服务，比如 milvus、etcd 这些可选服务放在单独 profile，开发时默认不启动，用降级方案，需要时加 --profile milvus 启动，节省开发机器资源。
    - 完整命令：docker compose up -d 启动核心服务，docker compose --profile all up -d 启动全部服务。
2. CI/CD 完整流程设计
  - 我们用 GitLab CI（或 GitHub Actions）做 CI/CD，流水线分几个阶段，核心特色是把 Skill 评测 Harness 作为质量门禁，AI 应用的变更必须通过效果评测才能合入和发布。
  - 阶段一：代码检查与单元测试（提交即触发）
    - 代码格式检查：Go 用 gofmt + golangci-lint，Python 用 black + isort + flake8/ruff，代码格式不规范直接失败，保证代码风格统一。
    - 静态分析：Go 用 go vet，Python 用 mypy（类型检查）+ bandit（安全扫描），提前发现潜在 bug 和安全问题。
    - 依赖安全扫描：扫描第三方依赖是否有已知漏洞，用 trivy 或 pip-audit。
    - 单元测试：Go 用 go test ./...，Python 用 pytest 跑单元测试和接口测试（Mock 外部依赖），生成覆盖率报告，核心模块覆盖率低于阈值（比如 70%）失败。
    - 这个阶段最快，几分钟完成，提交代码后立刻反馈基础问题，开发者本地也可以跑同样的检查。
  - 阶段二：构建与集成测试（MR 合入前触发）
    - 镜像构建：构建 Go 和 Python 服务的 Docker 镜像，用测试环境的标签，推送到镜像仓库。
    - 集成环境部署：把镜像部署到测试环境（用 Docker Compose 或 K8s），数据库迁移、服务启动，健康检查通过后进入下一步。
    - 集成测试：跑端到端集成测试，包括多轮对话流程、RAG 降级机制、ASR 质检流程、Token 统计等，验证服务间协作正常。
    - 数据库迁移测试：测试 SQL 迁移脚本能否正常执行，回滚脚本是否可用，防止生产环境迁移出问题。
  - 阶段三：AI 效果评测（核心质量门禁，MR 合入前必须通过）
    - 这是我们 AI 应用 CI/CD 最有特色的阶段，传统应用没有这一步：
    - 变更影响分析：检测本次 MR 变更了哪些 Skill、Prompt、检索逻辑、模型配置，只跑受影响的 Skill 的评测用例，节省时间；如果是基础框架变更，跑全量评测。
    - 执行评测 Harness：用 Pytest 驱动评测，加载对应 Skill 的评测数据集（每个 Skill 不少于 20 条），执行多种断言（关键词、结构化字段、语义相似度），生成评测报告。
    - 质量门禁判定：
      1. 用例数量检查：每个 Skill 评测用例不少于 20 条，不足直接失败。
      2. 通过率检查：整体通过率不低于基线阈值（比如 90%，核心 Skill 95%）。
      3. 回归检查（最重要）：和主干分支的基线评测结果对比，任何之前通过的用例现在失败了（回归），直接阻塞合入，必须解释原因或修复。
      4. 人工复核用例：标记为待人工复核的用例，必须在合入前完成复核，复核不通过按失败算。
    - 评测报告生成：生成包含通过率、失败用例详情、输入快照、数据集版本、代码版本（Git Commit）、Skill 版本的报告，评论到 MR 页面，评审者一眼就能看到本次变更对效果的影响。
    - 这个阶段是 AI 应用质量的核心保障，防止"改好一个场景，弄坏另一个场景"，也是推动 Prompt 调优从人工抽查转向自动化回归的关键。
  - 阶段四：安全扫描与合规检查
    - 镜像安全扫描：用 trivy 扫描构建好的镜像，检查是否有系统漏洞、恶意软件，高危漏洞必须修复才能发布。
    - 敏感信息检查：扫描代码和镜像里是否有硬编码的 API Key、密码、私钥等敏感信息，防止泄露。
    - License 检查：检查第三方依赖的 License 是否合规，避免法律风险。
    - 审计日志检查：确认涉及用户数据、大模型调用的操作都有审计日志，满足合规要求。
  - 阶段五：部署与发布（合并到主干后触发）
    - 测试环境自动部署：MR 合入后，自动部署到测试环境，跑冒烟测试，确认基本功能正常。
    - 生产环境灰度发布：
      1. 先部署到灰度环境（或切 10% 流量），观察核心指标（错误率、响应时间、评测效果、成本）。
      2. 灰度期间持续监控，有问题立刻回滚，没问题逐步放大流量（10% → 30% → 50% → 100%）。
      3. AI 应用特别关注效果指标，灰度期间抽样评测，确认新版本效果不下降再全量。
    - 回滚机制：每个版本保留历史镜像，一键回滚到上一个稳定版本，回滚时间控制在几分钟内，出问题快速恢复。
    - 数据库变更：数据库迁移脚本在发布前单独执行，遵循"向前兼容"原则，先加字段/表，再发布代码，最后清理旧字段，避免发布期间数据不一致。
  - 阶段六：发布后监控与验证
    - 发布后 1 小时重点值守，监控核心指标：服务可用性、接口错误率、响应时间、大模型调用成功率、Token 成本、用户反馈。
    - AI 效果专项监控：抽样线上问答，自动评估回答质量，和发布前对比，发现效果下降及时告警和回滚。
    - 发布完成后生成发布报告，记录版本、变更内容、发布时间、验证结果，归档备查。
3. CI/CD 中的特色实践和踩坑经验
  - 特色一：评测结果可追溯、可复现
    - 每次评测报告都记录 Git Commit、数据集版本、Skill 版本、模型版本，任何一次评测结果都可以复现，出了问题能精准定位是哪个版本的什么变更导致的。
    - 历史评测结果归档存储，可以做效果趋势分析，看每个 Skill 的质量是提升还是下降，用数据驱动优化。
  - 特色二：增量评测 + 全量评测结合
    - 普通 MR 只跑受影响的 Skill 评测（增量），几分钟出结果，不影响开发节奏；每天夜间跑全量评测，作为质量基线，也能发现增量评测没覆盖到的间接影响。
    - 发布前必须跑一次全量评测，确保发布版本整体质量达标。
  - 特色三：Prompt 变更和代码变更走同一套流程
    - Prompt 模板、Skill 配置都存在代码库里（配置即代码），变更走 MR 评审 + 评测门禁，和代码变更一样的流程，不会出现"有人偷偷改了 Prompt 导致效果下降，没人知道"的情况。
    - 这一点很重要，AI 应用里 Prompt 就是核心逻辑，必须和代码一样管理。
  - **踩坑一：最开始评测全量跑，一次十几分钟，大家嫌慢不愿意等，后来做了增量评测，普通 MR 几分钟出结果，大家就愿意用了，效率和质量兼顾。
  - **踩坑二：评测断言太严格，正常的表述差异也判失败，导致很多假失败，大家不信任评测结果，后来优化了断言策略，结构化字段精确校验 + 关键词 + 语义相似度结合，减少假失败，评测结果可信度提升。
  - **踩坑三：灰度发布只看技术指标（错误率、响应时间），没看 AI 效果指标，有一次发布后技术指标正常，但回答质量下降了，过了半天才发现，后来灰度期间必须抽样评测效果，和技术指标一起监控。
  - **踩坑四：数据库迁移和代码发布同时做，导致发布期间新旧代码读写不一致，出现数据错误，后来改成数据库变更提前执行，向前兼容，代码发布后再清理旧字段，就没再出问题。
4. 落地效果
  - CI/CD 流水线完善后，代码和 Prompt 变更的基础问题（格式、bug、安全）100% 在 CI 阶段拦截，线上低级故障基本为零。
  - 评测质量门禁上线后，Prompt 调优导致的回归问题 100% 在 MR 阶段发现，线上因为 Prompt 变更导致的效果下降从每月好几起降到基本为零。
  - 自动化发布 + 灰度 + 一键回滚，发布频率从每周一次提升到每天可以多次发布，发布风险大幅降低，迭代速度明显加快。
  - 环境一致性有了保障，Docker Compose 一键启动开发环境，新人入职半天就能跑起来整个系统，不用花几天搭环境。
  - 经验总结：AI 应用的 CI/CD，除了传统应用的代码检查、测试、部署，必须加上 AI 效果评测这个核心环节，把 Prompt 和模型效果纳入质量门禁，这是 AI 工程化和传统软件工程最大的区别之一。

第27题：你们的监控告警体系是怎么搭建的？AI 应用需要监控哪些特殊指标？
回答思路： 先讲整体监控架构（Prometheus + Grafana + 日志 + 链路追踪），再分基础设施、应用服务、AI 效果三层讲监控指标，重点讲 AI 应用特有的效果、成本、质量监控，体现你对可观测性的深度理解和 AI 场景的实战经验。
参考答案：
1. 监控告警体系整体架构
  - 我们用业界主流的可观测性三件套 + 业务监控，覆盖从基础设施到 AI 效果的全链路：
  - 指标监控（Metrics）：Prometheus 采集指标，Grafana 做可视化大盘，Alertmanager 做告警分发。
  - 日志监控（Logging）：ELK（Elasticsearch + Logstash + Kibana）或 Loki 收集服务日志，结构化存储，支持全文检索和日志告警。
  - 链路追踪（Tracing）：Jaeger / OpenTelemetry 做分布式链路追踪，Go 和 Python 服务都埋点，一次请求跨服务的完整调用链可追溯，每个环节耗时清晰。
  - AI 效果监控：这是 AI 应用特有的，用离线评测 + 线上抽样 + 用户反馈结合，监控回答质量、幻觉率、用户满意度等效果指标。
  - 告警渠道：飞书/钉钉/企业微信机器人 + 短信 + 邮件，按告警级别分发，P0 级故障电话通知，P1 即时消息，P2 邮件汇总。
2. 第一层：基础设施监控（基础保障）
  - 这是所有系统都需要的基础监控，保证底层资源稳定：
  - 服务器资源：CPU 使用率、内存使用率、磁盘使用率、磁盘 IO、网络带宽、TCP 连接数，设置阈值告警（CPU > 80% 持续 5 分钟、内存 > 85%、磁盘 > 80%）。
  - 容器监控：Pod/容器的 CPU、内存、重启次数、存活状态，K8s 节点状态、资源使用率，容器异常重启立刻告警。
  - 中间件监控：
    - MySQL：连接数、慢查询数、QPS、TPS、主从同步延迟、锁等待、表空间使用率，慢查询超过阈值告警。
    - Redis：内存使用率、命中率、QPS、连接数、主从同步状态、慢查询、大 key 数量，命中率低于 90%、内存超过 80% 告警。
    - 消息队列（Celery/Redis）：队列长度、消费延迟、消费成功率、死信队列数量，队列积压超过阈值告警。
    - 向量库（Milvus，如使用）：查询延迟、索引加载状态、内存占用、数据量。
  - 网络监控：服务间调用成功率、延迟、丢包率，DNS 解析时间，外部 API（大模型服务）的连通性和延迟。
  - 这一层的目标是：基础设施出问题第一时间发现，快速定位是哪台机器、哪个组件出问题。
3. 第二层：应用服务监控（业务稳定性）
  - 监控 Go 和 Python 服务的运行状态和接口质量：
  - 服务存活与健康：服务健康检查状态、实例数、启动时间，服务不可用、实例数少于预期立刻 P0 告警。
  - 接口核心指标（RED 原则）：
    - Rate（请求量）：每个接口的 QPS，按租户、按接口维度统计，流量突增突降告警。
    - Errors（错误率）：接口错误率（5xx、4xx 占比），错误率超过 1% 告警，5xx 错误必须告警。
    - Duration（延迟）：接口响应时间 P50/P95/P99，超过阈值告警（比如 P95 > 2s 持续 3 分钟）。
  - Go 服务特有指标：goroutine 数量（异常增长告警，防止 goroutine 泄漏）、GC 频率和停顿时间、内存分配、协程池队列长度、熔断状态（哪些服务熔断了）。
  - Python 服务特有指标：事件循环延迟（异步框架是否被阻塞）、工作进程数、内存占用、异常堆栈数量。
  - 业务流程指标：
    - 会话创建数、活跃会话数、平均会话轮次、会话完成率。
    - Skill 调用次数、成功率、平均耗时，按 Skill 维度统计，某个 Skill 失败率突增告警。
    - ASR 任务数、转写成功率、平均转写时长、质检报告生成数。
    - 评测任务执行数、通过率、平均耗时。
  - 依赖服务监控：
    - 大模型 API 调用成功率、平均响应时间、首字延迟（流式输出）、限流错误数，大模型服务故障或延迟突增立刻告警，这是 AI 应用最核心的外部依赖。
    - Embedding 服务调用成功率、延迟，降级触发次数（远程服务挂了降级到本地的次数），降级频繁说明远程服务不稳定。
    - 第三方服务（短信、邮件、存储）调用状态。
  - 这一层的目标是：服务出问题快速发现，定位到哪个接口、哪个服务、哪个依赖出问题，影响范围多大。
4. 第三层：AI 效果与质量监控（AI 应用特有，核心特色）
  - 这是 AI 应用和传统应用最大的区别，传统应用监控技术指标就行，AI 应用技术指标正常不代表效果好，必须专门监控回答质量和效果：
  - 检索质量指标（RAG 效果）：
    - 召回率：抽样评估检索结果的 Top-K 召回率，正确答案有没有被召回，低于阈值告警。
    - 召回相关性：召回结果和用户问题的相关度评分，用评估模型自动打分或人工抽样。
    - 空召回率：用户问题检索不到相关内容的比例，突增说明知识库有问题或用户提问方式变了。
    - 降级触发率：远程检索不可用降级到本地/关键词的比例，突增说明检索服务有问题。
  - 回答质量指标（生成效果）：
    - 回答准确率：抽样评估回答是否准确、有无幻觉，用自动评估模型 + 人工复核，准确率低于基线告警。
    - 幻觉率：回答中出现无依据、编造内容的比例，超过阈值告警，这是法律场景的红线指标。
    - 答案完整度：回答是否覆盖用户问题的所有要点。
    - 引用覆盖率：回答中标注引用来源的比例，法律场景要求有依据，引用率低说明可能在瞎编。
  - 用户反馈指标：
    - 用户点赞/点踩率：点踩率突增说明回答质量下降，立刻告警排查。
    - 转人工率：用户主动转人工的比例，突增说明 AI 回答不好，用户不满意。
    - 追问率：用户反复追问同一个问题的比例，高说明第一次回答没解决问题。
    - 用户满意度评分：会话结束后的满意度评分，低于阈值告警。
  - 效果漂移检测：
    - 设定效果基线（稳定运行时的准确率、幻觉率、点踩率），每日/每小时抽样评估，连续两个周期低于基线 5% 以上触发效果漂移告警，通知研发排查。
    - 自动排查可能原因：是知识库更新了、Prompt 改了、模型版本变了、还是用户提问分布变了，给出排查方向。
    - 这是我们项目中很有特色的部分，很多 AI 应用效果慢慢下降没人发现，等用户投诉就晚了，主动检测能提前发现。
  - Bad case 自动收集：
    - 自动收集点踩的回答、转人工的会话、低置信度回答、用户投诉的内容，进入 bad case 池，定期分析，补充到评测数据集，形成"发现问题 → 补充用例 → 优化 → 回归"的闭环。
  - 这一层的目标是：AI 回答质量下降第一时间发现，不用等用户投诉，定位是检索、生成还是知识库的问题。
5. 第四层：成本监控（AI 应用特有，直接关系钱）
  - AI 应用大模型调用是真金白银，成本监控非常重要，传统应用没有这一层：
  - 整体成本指标：
    - 每日/每周/每月大模型调用总费用、Embedding 费用、总 Token 消耗，和预算对比，超预算告警。
    - 成本趋势：成本环比/同比变化，突增告警，防止异常调用导致成本暴增。
  - 维度拆分成本：
    - 按租户：每个律所租户的调用量和费用，哪个租户用得多、费用高，支持计费和成本分摊。
    - 按 Skill：每个 AI Skill 的 Token 消耗和费用，哪个 Skill 最耗钱，针对性优化（比如法律问答 RAG 召回内容太多，优化 Top-K）。
    - 按会话/用户：高消耗用户和会话，识别异常刷量或超长无效对话。
    - 按模型：不同模型的调用量和费用占比，为模型选型提供数据（比如"用 DeepSeek-V3 比 V2 成本高 20%，效果提升 5%，值不值"）。
    - 按 Token 类型：输入 Token、输出 Token、Embedding Token 各自占比，输入占比高说明上下文太长，优化召回和历史摘要；输出占比高说明回答太长，优化 Prompt 控制长度。
  - 成本异常告警：
    - 单小时/单日费用超过阈值告警，防止接口被刷或死循环调用导致成本暴增。
    - 单用户/单租户调用量异常突增告警，识别恶意调用。
    - 平均单次调用成本突增告警，说明可能有异常（比如上下文无限增长、召回了太多内容）。
  - 成本优化效果跟踪：
    - 每次成本优化（比如加缓存、精简上下文、模型路由）后，跟踪成本变化，量化优化效果，用数据证明优化价值。
  - 这一层的目标是：钱花得清清楚楚，异常成本第一时间发现，成本优化有数据支撑。
6. 日志与链路追踪的实践
  - 结构化日志：所有服务输出 JSON 格式结构化日志，包含 timestamp、service、level、trace_id、span_id、tenant_id、session_id、user_id、message、error 等字段，方便检索和关联。
  - Trace ID 全链路透传：请求从网关进入生成 trace_id，Go → Python → 数据库 → 大模型调用，全链路透传，出问题用 trace_id 能拉到完整的调用链和日志，快速定位。
  - AI 调用专属日志：每次大模型调用记录完整的审计日志（输入摘要、输出摘要、Token 数、费用、模型、耗时、状态），存在 MySQL 和日志系统，支持按会话、按 Skill、按时间查询，满足审计和排查需求。
  - 错误日志告警：ERROR 级别日志数量突增告警，特定错误（比如大模型调用失败、数据库连接失败）出现立刻告警。
  - 链路追踪可视化：Jaeger 界面看一次请求的完整调用树，每个服务、每个数据库查询、每个外部调用的耗时和状态，性能瓶颈一目了然，比如发现大模型调用占了 80% 时间，就优化模型调用或加缓存。
7. 告警分级与处理流程
  - P0（紧急）：服务不可用、核心功能完全故障、数据泄露风险、成本异常暴增，电话 + 短信 + 即时消息通知，15 分钟内响应，立即处理。
  - P1（高）：核心接口错误率 > 5%、P95 延迟严重超标、大模型服务故障、效果指标严重下降，即时消息通知，30 分钟内响应。
  - P2（中）：非核心接口异常、中间件告警、效果指标轻度下降、成本接近预算，即时消息通知，工作日处理。
  - P3（低）：提示性告警、趋势性指标变化、建议优化项，邮件汇总，定期处理。
  - 告警治理：
    - 避免告警风暴，设置告警抑制（同一问题短时间不重复告警）、告警聚合（相关告警合并）。
    - 定期复盘告警，无效告警、误报及时调整阈值或关闭，保证告警的可信度，避免"狼来了"效应。
    - 每个告警都有对应的处理预案（oncall runbook），收到告警知道怎么排查、怎么处理，不用临时想。
8. 落地效果和经验总结
  - 全链路监控体系上线后，故障发现时间从平均几十分钟（靠用户反馈）降到几分钟（自动告警），故障平均修复时间也大幅缩短，因为有 trace_id 和完整日志，定位很快。
  - AI 效果监控和成本监控是 AI 应用的特色，上线后成功发现了几次效果缓慢下降和成本异常突增的情况，提前处理，没有造成大的影响，这是传统监控做不到的。
  - 经验总结：
    1. AI 应用的监控不能只盯技术指标，必须加上效果监控和成本监控，这是 AI 应用和传统应用最大的区别，技术指标正常不代表用户体验好、不代表没多花钱。
    2. 可观测性三件套（Metrics、Logging、Tracing）是基础，必须做全，trace_id 全链路透传是排查问题的利器，AI 调用链路长，没有 trace 根本没法排查。
    3. 告警要分级、要治理，保证每个告警都是有用的，告警太多没人看等于没有告警。
    4. 效果监控要接受"抽样+概率"的特点，不可能每条都人工看，用自动评估模型 + 抽样人工 + 用户反馈结合，建立效果基线，做漂移检测，主动发现问题，而不是等用户投诉。
    5. 成本监控对 AI 应用至关重要，大模型调用是按 Token 计费的，异常调用、死循环、上下文膨胀都会导致成本暴增，必须实时监控和告警，钱的问题无小事。

第28题：结合这个项目，说说你对 AI 应用工程化的理解，和传统软件工程有什么不同？
回答思路： 这是一道开放的认知题，结合项目实战经验，从不确定性、质量保障、迭代方式、团队协作等多个维度对比 AI 工程化和传统软件工程的差异，体现你对 AI 工程化的深度思考和体系化认知，是拉开和普通开发者差距的题。
参考答案：
1. 我对 AI 应用工程化的整体理解
  - 做这个项目之前，我以为 AI 应用就是"调大模型 API + 写点 Prompt"，做了之后才发现，把一个 AI 能力从 Demo 变成稳定、可维护、可迭代的生产级产品，需要一整套工程化的方法论和工具链，这就是 AI 应用工程化。
  - 它不是传统软件工程加个大模型调用，而是从需求、开发、测试、部署、运维、迭代全流程都因为 AI 的不确定性而发生了本质变化，需要新的方法论、新的工具、新的质量标准。
  - 我们这个项目（LexAgent 律所 AI 平台）就是一个典型的 AI 工程化实践，从 Skill 标准化、评测 Harness、CI 质量门禁、多级降级、成本审计、效果监控，都是在解决 AI 应用生产落地的工程化问题。
2. 核心区别一：输出的确定性 vs 不确定性（最本质的区别）
  - 传统软件工程：输出是确定性的，给定输入，代码逻辑确定，输出就确定，1+1 永远等于 2，出了错一定是代码 bug，能精准定位和复现。
  - AI 应用工程化：输出是概率性的、不确定的，同样的输入，大模型两次输出可能表述不一样，甚至有时对有时错，还有幻觉问题。出了"错"不一定是代码 bug，可能是 Prompt 不好、检索没召回、模型能力不够、上下文太长，原因复杂且难以复现。
  - 带来的工程化变化：
    - 不能用传统的"精确断言"做测试，必须发展多层断言（结构化字段 + 关键词 + 语义相似度 + 人工复核），接受"大致对"而不是"完全等"。
    - 必须有降级和兜底机制，不能假设大模型永远返回正确格式和内容，输出校验、格式修正、失败重试、兜底回答都是标配。
    - 代码逻辑要做防御性编程，对大模型返回的内容做严格校验，不能信任，防止格式错误、内容违规导致程序崩溃或业务事故。
  - 我们项目的实践：Skill 输出 Schema 校验 + 多种断言方式的评测 Harness + 多级降级机制，都是在应对不确定性。
3. 核心区别二：核心资产从"代码"变成"代码 + 数据 + Prompt + 模型"
  - 传统软件工程：核心资产是代码，代码写好了功能就定了，数据是用户产生的，模型（如果有）是固定的算法。
  - AI 应用工程化：核心资产是四样东西的组合：
    1. 代码：业务逻辑、工程框架、工具集成，这是基础。
    2. 数据：知识库、评测数据集、用户对话数据，数据质量直接决定 AI 效果，"垃圾进垃圾出"。
    3. Prompt：Prompt 就是 AI 应用的核心逻辑，改 Prompt 就像改代码，直接影响输出质量和行为，必须像代码一样管理。
    4. 模型：用哪个模型、模型版本、模型参数，也是核心决策，影响效果、成本、速度。
  - 带来的工程化变化：
    - Prompt 和配置必须纳入版本管理，走代码评审流程，不能随便改，改了必须有评测验证，我们项目里 Prompt 都存在代码库，变更走 MR + 评测门禁。
    - 评测数据集是核心资产，需要持续建设、版本管理、质量治理，不是一次性的工作，我们每个 Skill 不少于 20 条用例，还在持续补充 bad case。
    - 知识库需要全生命周期管理，从清洗、切片、入库、更新、版本、回滚，都有工程化流程，不是随便扔几份文档就行。
    - 模型选型需要数据驱动，对比效果、成本、速度，有量化评估，不是拍脑袋选。
  - 我们项目的实践：Prompt 配置化 + 版本管理、评测数据集版本化、知识库全链路治理、Token 成本审计支撑模型选型，都是在管理这些新的核心资产。
4. 核心区别三：质量保障从"功能测试"变成"功能测试 + 效果评测"
  - 传统软件工程：质量保障主要是功能测试，测功能对不对、有没有 bug、性能够不够，用例是确定的，通过/失败是非黑即白的，自动化测试覆盖率是核心指标。
  - AI 应用工程化：功能正常只是基础，更重要的是"效果好不好"——回答准不准、幻觉多不多、用户满不满意，这些是模糊的、需要量化评估的，而且效果会因为 Prompt、模型、数据的变化而波动，需要持续评测。
  - 带来的工程化变化：
    - 必须建立专门的 AI 效果评测体系，包括评测数据集、多种断言方式、自动化评测工具、效果量化指标，这是传统测试没有的。
    - 评测必须接入 CI/CD 成为质量门禁，每次 Prompt、模型、检索逻辑变更，必须跑全量评测，防止回归，因为 AI 的回归问题很隐蔽，不跑全量根本发现不了。
    - 线上需要效果监控和漂移检测，因为效果可能缓慢下降，不能等用户投诉，要主动抽样评估，和基线对比，发现异常及时告警。
    - 测试金字塔变了：底层单元测试测确定性逻辑，中层接口测试测流程，上层效果评测测 AI 质量，越往上越"软"、越贵、数量越少，但越重要。
  - 我们项目的实践：自研 Skill 评测 Harness、320 条评测用例质量基线、CI 质量门禁（用例数量 + 通过率 + 回归检查）、线上效果漂移检测，形成了完整的 AI 质量保障体系，这也是我们项目最有特色的工程化实践。
5. 核心区别四：迭代方式从"功能迭代"变成"效果驱动的持续优化"
  - 传统软件工程：迭代主要是加功能、修 bug，版本发布有明确的功能清单，功能做完了就可以上线，上线后主要是修 bug，不需要持续调优。
  - AI 应用工程化：功能只是骨架，效果才是核心，效果优化是持续的、没有终点的——Prompt 可以一直调、知识库可以一直补、检索策略可以一直优化、模型可以一直换，每次优化都需要数据验证效果，迭代周期更短、更频繁，更像"调参"而不是"开发功能"。
  - 带来的工程化变化：
    - 迭代节奏更快，需要支持 Prompt、配置的快速变更和验证，不能每次改个 Prompt都走完整的开发发布流程，我们的 Skill 和 Prompt 都是配置化的，可以快速调整并跑评测验证。
    - 数据驱动迭代，每次优化都要有评测数据证明效果提升，不能凭感觉说"我觉得变好了"，我们每次 Prompt 调优都跑评测，用通过率和效果指标说话。
    - 建立 bad case 闭环，线上发现的问题自动收集，补充到评测集，优化后回归验证，形成"发现问题 → 分析 → 优化 → 评测 → 上线"的持续迭代闭环，而不是一次性开发。
    - A/B 测试和灰度发布很重要，效果优化不能全量直接上，先灰度或 A/B 对比，确认效果提升再全量，因为有时候你以为优化了，实际效果反而下降了。
  - 我们项目的实践：配置化 Skill + Prompt 快速调整、评测 Harness 数据驱动优化、bad case 自动收集回流、灰度发布 + 效果验证，形成了持续优化的闭环。
6. 核心区别五：成本和性能的权衡更复杂
  - 传统软件工程：成本主要是服务器和人力，性能优化主要是响应时间和吞吐量，相对固定，优化手段成熟（缓存、数据库优化、异步化）。
  - AI 应用工程化：成本结构完全不同，大模型调用是按 Token 计费的持续可变成本，用得越多花得越多，而且效果和成本强相关——用更好的模型、更长的上下文、更多的召回，效果更好但更贵，需要在效果、成本、速度之间做复杂权衡，而且成本可能因为异常调用暴增，必须精细化管控。
  - 带来的工程化变化：
    - 必须有精细的 Token 统计和成本核算，每次调用都记录用量和费用，按多维度归因（租户、Skill、会话、模型），我们项目做了完整的 LLM 调用审计和单价快照机制。
    - 必须有成本优化手段，而且不能牺牲效果，比如高频问题缓存、动态 Top-K、上下文压缩、模型路由（简单问题用便宜模型），我们项目通过这些手段降了 30% 成本。
    - 必须有成本监控和告警，防止异常调用、死循环、上下文膨胀导致成本暴增，钱的问题无小事。
    - 性能优化不仅是接口响应时间，还有大模型首字延迟、流式输出体验，需要 SSE、流式调用、异步处理等专门优化。
  - 我们项目的实践：Token 统计 + 单价快照 + 成本审计、多级缓存、动态模型路由、上下文摘要压缩、成本监控告警，形成了完整的成本管控体系。
7. 核心区别六：系统设计更强调容错、降级和兜底
  - 传统软件工程：依赖的服务（数据库、缓存、其他微服务）相对稳定，出问题是异常情况，容错是锦上添花，很多系统没有完善的降级也能跑。
  - AI 应用工程化：依赖的大模型 API、Embedding 服务、向量库都是外部服务，不稳定是常态——超时、限流、报错、服务降级、模型更新，经常发生，而且大模型本身就可能返回错误格式、违规内容，所以容错、降级、兜底不是可选的，是必须的，是系统设计的核心部分。
  - 带来的工程化变化：
    - 必须有多级降级机制，核心链路不能因为一个依赖挂了就不可用，我们的 RAG 检索做了"远程知识库 → 本地向量库 → 关键词匹配"三级降级，外部服务挂了依然能基本可用。
    - 必须有完善的异常处理，大模型调用超时、返回格式错误、内容违规，都要有对应的处理逻辑，重试、修正、兜底，不能让程序崩溃或把错误直接抛给用户。
    - 必须有熔断和限流，保护下游服务也保护自己，防止级联故障和成本暴增，我们 Go Harness 做了完整的熔断状态机、指数退避重试、限流。
    - 必须有人工接管和兜底，AI 处理不了的、高风险的、低置信度的，自动转人工，不能硬着头皮回答，尤其是法律这种高风险场景。
  - 我们项目的实践：RAG 三级降级、Harness 运行时治理（超时、重试、熔断、上下文隔离）、人工接管队列、输出校验和兜底，都是在应对依赖的不确定性。
8. 核心区别七：团队协作和技能要求更综合
  - 传统软件工程：分工明确，后端、前端、测试、运维、产品，各干各的，技能边界清晰。
  - AI 应用工程化：需要更综合的能力和更紧密的协作，开发工程师要懂 AI 基本原理（Prompt、RAG、Agent），算法/AI 同学要懂工程化（测试、部署、监控），产品要理解 AI 的能力边界，测试要会做效果评测，传统的分工边界模糊了，需要"AI 全栈工程"能力。
  - 带来的变化：
    - 工程师不能只会写业务代码，要理解大模型的能力和局限，会写 Prompt、会做 RAG、会调 Agent，这是新的核心技能。
    - 测试工程师不能只会功能测试，要会构建评测数据集、设计断言、做效果评估，AI 评测是新的测试方向。
    - 产品经理不能只提功能需求，要理解 AI 能做什么不能做什么，会设计效果验收标准，而不是只验收功能。
    - 团队需要更多跨职能协作，AI 效果优化需要产品、开发、测试、运营一起参与，不是开发一个人能搞定的。
  - 我们项目的实践：Go 和 Python 混合架构，开发同学既要懂后端工程也要懂 AI 能力，评测体系需要开发和业务一起建用例，知识库运营需要业务和技术配合，是典型的跨职能协作。
9. 总结：AI 应用工程化的核心思维
  - 做这个项目最大的收获是建立了 AI 工程化的思维，我总结为几点：
    1. 接受不确定性：不要追求 100% 正确，要通过工程手段把错误率降到可接受范围，用多层校验、兜底、降级保障系统稳定。
    2. 数据驱动一切：效果好不好、成本高不高、优化有没有用，都用数据说话，不要凭感觉，评测体系和监控体系是基础。
    3. 质量是持续的过程：不是上线就完事了，效果会漂移，数据会变化，需要持续评测、持续监控、持续优化，建立闭环。
    4. 成本意识贯穿始终：AI 调用是真金白银，从设计到开发到优化都要考虑成本，在效果和成本之间找最优解。
    5. 工程化是 AI 落地的关键：Demo 到产品之间隔着一整套工程化体系，Skill 标准化、评测、CI 门禁、降级、监控、成本管控，这些"不性感"的工程工作，才是 AI 真正能稳定服务用户的核心。
  - 未来 AI 应用会越来越多，AI 工程化能力会成为工程师的核心竞争力，不是会调 API 就行，而是能把 AI 能力做成稳定、可靠、低成本、可迭代的生产级产品，这也是我接下来继续深耕的方向。

第29题：如果让你从零搭建一个类似的企业级 AI 平台，你的整体架构和技术选型会怎么设计？
回答思路： 这是一道架构设计开放题，结合项目经验，从业务场景出发，分层讲整体架构和技术选型，讲清楚每个选型的理由，体现你的架构设计能力和技术选型判断力，注意不要过度设计，要贴合企业级 AI 平台的实际需求。
参考答案：
1. 架构设计的前提：先明确业务场景和核心诉求
  - 从零搭建不能上来就堆技术，先想清楚做什么、给谁用、核心诉求是什么，假设是类似 LexAgent 的面向垂直行业（比如律所、金融、医疗）的企业级 AI 平台，核心诉求是：
    - 支持多种 AI 业务场景（智能问答、文档审查、质检、Agent 自动化）
    - 多租户隔离，数据安全合规
    - 效果可量化、质量可保障，不能经常出幻觉
    - 成本可控，大模型调用费用可管可优化
    - 高可用，外部 AI 服务故障时核心功能依然可用
    - 可扩展，新场景、新模型、新工具能快速接入
  - 基于这些诉求，我会设计分层架构，技术选型优先选成熟、生态好、团队熟悉的，不盲目追新，平衡性能、开发效率和成本。
2. 整体分层架构设计
  - 我会分成六层，从下到上职责清晰，高内聚低耦合：
┌─────────────────────────────────────────────────┐
│  接入层：API 网关 / 鉴权 / 限流 / 路由          │
├─────────────────────────────────────────────────┤
│  业务应用层：场景化服务（问答/审查/质检/Agent） │
├─────────────────────────────────────────────────┤
│  AI 能力层：Skill 标准化 / Agent 编排 / RAG 检索 │
├─────────────────────────────────────────────────┤
│  模型服务层：大模型网关 / Embedding / ASR / 多模型路由│
├─────────────────────────────────────────────────┤
│  数据层：MySQL / Redis / 向量库 / 对象存储 / ES  │
├─────────────────────────────────────────────────┤
│  基础设施层：容器编排 / CI/CD / 监控告警 / 日志链路│
└─────────────────────────────────────────────────┘
1. 各层详细设计与技术选型
  - 第一层：接入层（网关）
    - 职责：统一入口，鉴权、限流、路由、协议转换、跨域、日志、Trace ID 生成。
    - 技术选型：Go + Gin/Hertz 自研轻量网关，或者用 APISIX/Kong 等开源网关，小团队自研更灵活，大团队用成熟网关。
    - 选型理由：网关是性能瓶颈，Go 并发性能好，适合做网关；鉴权、限流、多租户识别这些通用逻辑下沉到网关，后端服务不用重复实现。
    - 关键设计：JWT + API Key 双鉴权，按租户/用户/接口多维度限流，Trace ID 全链路透传，请求日志结构化。
  - 第二层：业务应用层（场景服务）
    - 职责：面向具体业务场景的服务，比如智能客服问答服务、合同审查服务、通话质检服务、案件辅助 Agent 服务，每个服务独立部署、独立扩缩容。
    - 技术选型：Python + FastAPI 为主（AI 逻辑多的场景），Go + Gin 为辅（重业务逻辑、高并发的场景），混合架构，按场景选语言。
    - 选型理由：
      - AI 逻辑重的场景（RAG、Agent、Prompt 处理）用 Python，LangChain/LangGraph 生态成熟，开发快。
      - 业务逻辑重、高并发、对性能要求高的场景（工单、用户、计费）用 Go，性能好、稳定。
      - 不要为了技术栈统一强行用一种语言，合适的场景用合适的语言，通过 HTTP/gRPC 通信，接口契约解耦。
    - 关键设计：服务无状态，水平扩容；每个服务有独立的数据库 schema，按业务域拆分；服务间调用有超时、重试、熔断。
  - 第三层：AI 能力层（核心平台层）
    - 职责：这是 AI 平台的核心，把 AI 能力标准化、可复用，包括 Skill 标准化管理、Agent 编排引擎、RAG 检索服务、工具调用框架。
    - 技术选型：
      - Skill 框架：自研轻量 Skill 标准（输入 Schema、执行逻辑、输出 Schema、版本），Python 侧用 Pydantic 做 Schema 校验，Go 侧做调度和治理。
      - Agent 编排：LangGraph（Python）做复杂多轮 Agent 编排，简单场景用自研轻量状态机，不要所有场景都上重型框架。
      - RAG 检索：自研检索服务，支持 BM25 + 向量混合检索、多级降级，用 LangChain 组件做基础，自己封装业务逻辑。
      - 工具调用：MCP 协议标准化工具接入，新工具按 MCP 规范封装，Agent 可以统一调用。
    - 选型理由：
      - Skill 标准化是平台可扩展的关键，新场景只需组合现有 Skill + 开发少量新 Skill，不用从零开始。
      - LangGraph 适合复杂流程编排，状态管理、分支、人工介入支持好，比自己从零写 Agent 框架效率高。
      - RAG 核心逻辑要自己掌控，检索策略、降级、切片这些和业务强相关，不能完全依赖框架，框架只做基础组件。
      - MCP 是工具接入的标准趋势，提前按 MCP 设计，后续生态兼容性好。
    - 关键设计：
      - Skill 配置化，Prompt、参数、模型选择都可配置，不用改代码就能调整。
      - 所有 AI 调用统一走能力层，做统一的鉴权、审计、Token 统计、限流、缓存，业务层不用重复实现。
      - RAG 必须有多级降级，外部 Embedding/向量库挂了，本地向量 + 关键词匹配兜底，保证核心可用。
  - 第四层：模型服务层（模型网关）
    - 职责：统一管理所有模型调用，包括大语言模型、Embedding 模型、ASR 模型，做多模型路由、降级、成本统计、缓存、限流，业务层不直接调第三方 API。
    - 技术选型：Go 自研模型网关（性能好，适合做代理和治理），支持 OpenAI 兼容协议，接入 DeepSeek、通义、文心、本地开源模型等。
    - 选型理由：
      - 模型网关是 AI 平台的核心基础设施，所有模型调用都经过这里，统一做治理，业务方不用关心用哪个模型、怎么鉴权、怎么计费。
      - Go 做网关性能高、并发好，适合做代理、限流、统计这些逻辑。
      - 支持多模型是必须的，不能绑定一家厂商，做模型路由和降级，一家挂了切另一家，也能按场景选性价比最高的模型。
    - 关键设计：
      - 统一 OpenAI 兼容接口，业务方按标准接口调用，网关路由到具体模型，切换模型不用改业务代码。
      - 动态模型路由：按任务类型（简单/复杂）、成本、延迟、效果自动选模型，简单问题用便宜模型，复杂问题用好模型。
      - 统一降级：主模型故障自动切备用模型，Embedding 服务故障切本地预计算向量。
      - 统一 Token 统计和成本核算：每次调用记录输入/输出 Token、费用、单价快照，按多维度归因，这是成本管控的基础。
      - 统一缓存：高频问题的 Embedding 结果、问答答案缓存，降低调用成本。
      - 统一限流：按租户、按模型、按接口限流，防止超用和成本暴增。
  - 第五层：数据层
    - 职责：存储业务数据、缓存、向量、文件、日志，是平台的数据底座。
    - 技术选型：
      - 业务数据库：MySQL，成熟稳定，生态好，企业级应用首选，分库分表用 ShardingSphere 或业务层分片。
      - 缓存与会话：Redis，性能高，数据结构丰富，除了缓存还能做会话、分布式锁、限流、轻量队列、降级向量存储，一物多用。
      - 向量数据库：小规模用 Redis + NumPy 本地向量（轻量，不用额外组件），中大规模用 Milvus（开源、分布式、性能好、支持标量过滤），不要一开始就上重型向量库，按需选择。
      - 对象存储：MinIO（私有部署）或 S3，存文档、音频、生成的报告等非结构化数据。
      - 全文检索：Elasticsearch，做 BM25 关键词检索、日志存储、全文搜索，和向量检索配合做混合检索。
    - 选型理由：
      - 优先选成熟、团队熟悉的组件，降低运维成本，MySQL、Redis、ES 都是标配，运维经验丰富。
      - 向量库按规模选，小团队小数据量用轻量方案，不要为了"技术先进"上 Milvus 增加运维负担，数据量上来了再迁移。
      - 非结构化数据用对象存储，不要存数据库，成本低、扩展性好。
    - 关键设计：
      - 多租户数据隔离：所有业务表带 tenant_id，ORM 自动过滤；向量库按租户物理隔离或强过滤；缓存 Key 带租户前缀。
      - 冷热数据分离：历史会话、历史报告等冷数据归档，主表只存热数据，控制单表大小。
      - 数据备份：MySQL 定期备份，对象存储多副本，重要数据不能丢。
      - 敏感数据加密：客户信息、合同内容等敏感数据加密存储，符合数据安全合规。
  - 第六层：基础设施与工程化层
    - 职责：容器编排、CI/CD、监控告警、日志链路、评测体系，是平台稳定运行和持续迭代的保障。
    - 技术选型：
      - 容器编排：开发测试用 Docker Compose（简单，一键启动），生产用 Kubernetes（弹性伸缩、高可用、服务发现）。
      - CI/CD：GitLab CI / GitHub Actions，流水线包含代码检查、单元测试、镜像构建、集成测试、AI 效果评测门禁、灰度发布。
      - 监控告警：Prometheus + Grafana（指标），ELK/Loki（日志），Jaeger（链路追踪），Alertmanager（告警），飞书/钉钉通知。
      - 评测体系：自研评测 Harness，Pytest 驱动，支持多种断言，接入 CI 做质量门禁，线上效果漂移检测。
    - 选型理由：
      - 都是业界主流方案，生态成熟、文档多、团队容易上手，不用自研造轮子。
      - AI 效果评测是 AI 平台特有的，必须自研或专门建设，传统 CI 工具不自带，这是质量保障的核心。
    - 关键设计：
      - CI 必须包含 AI 效果评测门禁，Prompt/Skill/模型变更必须跑评测，防止回归，这是 AI 平台和传统应用最大的区别。
      - 监控必须包含 AI 特有指标：效果指标（准确率、幻觉率、点踩率）、成本指标（Token 消耗、费用）、降级触发率，不能只监控技术指标。
      - 全链路 Trace ID 透传，Go → Python → 模型 → 数据库，一次请求完整可追溯。
      - 灰度发布 + 一键回滚，AI 效果变更必须灰度验证，确认效果不下降再全量。
2. 核心架构设计原则
  - 原则一：分层解耦，能力下沉
    - 通用能力（鉴权、限流、模型调用、Token 统计、RAG 检索）下沉到平台层，业务层只关心业务逻辑，不要每个业务都重复造轮子。
    - 层与层之间通过标准接口通信，可独立替换、独立扩容，比如换模型厂商只改模型网关，业务层无感知。
  - 原则二：多租户与安全优先
    - 从第一天就做多租户隔离，数据安全是企业级应用的生命线，不要后补，后补代价极大。
    - 敏感数据加密、操作审计、权限控制，这些是企业客户的基本要求，必须有。
  - 原则三：容错降级是标配，不是可选
    - AI 依赖的外部服务不稳定是常态，从设计上就考虑多级降级、重试、熔断、兜底，核心功能不能因为一个依赖挂了就不可用。
    - 高风险场景有人工接管，AI 处理不了的转人工，不要硬答。
  - 原则四：效果和成本双驱动
    - 从设计上就考虑效果可量化（评测体系）和成本可管控（Token 统计、模型路由、缓存），这两个是 AI 平台的核心指标，不是上线后再补。
    - 所有优化都用数据验证，效果提升多少、成本降低多少，量化说话。
  - 原则五：不要过度设计，按需演进
    - 不要一开始就上微服务、K8s、Milvus、各种重型组件，小团队先用模块化单体 + Docker Compose + 轻量方案，跑通业务验证价值，再按瓶颈逐步拆分和升级。
    - 技术选型优先选团队熟悉、成熟稳定的，不要为了追新用没经验的技术，增加风险和运维成本。
    - 架构要预留扩展空间（比如接口标准化、模块解耦），方便后续演进，但不要提前实现不需要的复杂度。
3. 分阶段落地路线图
  - 从零搭建不要一步到位，分阶段落地，小步快跑，快速验证：
  - 第一阶段（1-2 个月）：最小可用版本（MVP）
    - 目标：跑通核心场景，验证业务价值。
    - 做什么：Docker Compose 编排，MySQL + Redis，一个核心 AI 场景（比如智能问答），基础 RAG 检索，单模型调用，基础 Skill 框架，简单的前端界面。
    - 不做什么：微服务、K8s、多租户高级特性、复杂评测体系，先把核心流程跑通。
  - 第二阶段（2-4 个月）：平台化与质量保障
    - 目标：提升稳定性和效果，建立质量和成本体系。
    - 做什么：Skill 标准化完善，评测 Harness + CI 质量门禁，模型网关（多模型路由 + Token 统计 + 成本核算），RAG 多级降级，多租户数据隔离，基础监控告警，1-2 个新业务场景。
    - 价值：从"能用"到"好用、稳定、质量可控"，建立 AI 工程化体系。
  - 第三阶段（4-6 个月）：规模化与生态
    - 目标：支持更多场景，提升性能和扩展性，完善运营体系。
    - 做什么：微服务拆分（按业务域），K8s 部署，向量库升级（Milvus），Agent 编排平台，MCP 工具生态，完善的监控（AI 效果 + 成本），灰度发布，知识库运营平台，更多业务场景接入。
    - 价值：平台可扩展，支持大规模业务，形成 AI 能力生态。
  - 第四阶段（6 个月以上）：持续优化与智能化
    - 目标：效果持续优化，成本持续降低，探索高级能力。
    - 做什么：效果持续迭代（bad case 闭环），成本优化（缓存、模型蒸馏、本地模型），多模态能力（文档理解、图像、语音），Agent 自动化复杂任务，私有化部署支持，行业解决方案沉淀。
  - 每个阶段都有明确的目标和产出，不盲目加功能，业务价值驱动。
4. 可能遇到的挑战和应对
  - 挑战一：AI 效果达不到预期，用户不满意
    - 应对：不要只靠大模型，RAG 知识库质量是关键，投入精力做数据治理；建立评测体系，用数据驱动优化；高风险场景人工兜底，不要追求 100% 自动化；持续收集 bad case 迭代。
  - 挑战二：大模型成本太高，入不敷出
    - 应对：模型路由（简单问题用便宜模型）、高频问题缓存、上下文压缩、Prompt 优化减少 Token、本地开源模型替代部分场景、按租户计费分摊成本，从设计上就做成本管控。
  - 挑战三：多租户数据安全和隔离
    - 应对：从第一天就做租户隔离，框架自动保证不靠人自觉；敏感数据加密；操作审计；权限最小化；定期安全扫描；重要客户物理隔离。
  - 挑战四：外部服务不稳定影响可用性
    - 应对：多级降级（远程 → 本地 → 兜底）；多模型多厂商备份；熔断限流；核心功能弱依赖外部服务；本地缓存和兜底方案。
  - 挑战五：团队 AI 工程化能力不足
    - 应对：先从简单场景入手，建立标准规范和工具链，降低 AI 开发门槛；培训和分享，提升团队 AI 认知；核心平台由有经验的同学搭建，业务方基于平台开发，不用每个人都懂底层。
5. 总结
  - 企业级 AI 平台的架构设计，核心不是堆多少新技术，而是围绕业务价值，在效果、成本、稳定性、可扩展性之间找平衡，AI 的不确定性决定了工程化体系（评测、降级、成本管控、效果监控）比传统应用更重要。
  - 技术选型优先成熟、团队熟悉、适合当前阶段的，不要过度设计，预留扩展空间，按需演进，小步快跑，先验证价值再逐步完善。
  - 最核心的一点：AI 平台的护城河不是用了什么框架什么模型，而是工程化体系（标准化 Skill、评测质量门禁、成本管控、效果闭环）和高质量的行业数据，这些是需要时间沉淀的，也是别人短期抄不走的，这也是我们做 LexAgent 项目最大的收获。

第30题：做这个项目过程中，你遇到的最大的技术挑战是什么？怎么解决的？有什么收获？
回答思路： 这是面试必问的开放题，选一个真实有分量的挑战，结合项目特色（AI 应用的不确定性、工程化难点），讲清楚背景、挑战、解决过程、最终效果和收获，要真实可信，有细节有数据，体现你的问题解决能力和深度思考。
参考答案：
1. 我遇到的最大技术挑战：AI 应用的质量保障和效果可量化问题
  - 具体来说，就是项目中期我们遇到了一个非常头疼的问题：Prompt 调优和 Skill 变更完全靠人工抽查，质量不可控，经常出现"改好一个场景，弄坏另一个场景"的回归问题，而且效果好不好全凭感觉，没有量化标准，线上偶尔出现回答质量下降的情况，等用户投诉才发现，非常被动。
  - 这个问题是 AI 应用和传统应用最大的区别带来的，传统应用改代码跑单元测试就行，AI 应用改 Prompt，输出是不确定的，传统测试方法根本覆盖不了，这也是我们从"做 Demo"走向"生产级产品"遇到的最大门槛。
2. 问题的具体表现和带来的痛点
  - 当时项目已经有 5-6 个 Skill 上线，每个 Skill 有自己的 Prompt 和逻辑，问题集中在几个方面：
  - 痛点一：回归问题频发，防不胜防
    - 有一次法律问答 Skill 优化了 Prompt，解决了"离婚财产分割"类问题的回答质量，上线后发现"劳动仲裁时效"类问题的回答反而变差了，因为 Prompt 改动影响了整体的回答风格和边界，而我们只测了优化的场景，没跑全量，上线后用户投诉才发现。
    - 类似的情况发生了好几次，每次改 Prompt 都提心吊胆，不知道会不会影响其他场景，大家都不敢大胆优化，迭代速度很慢。
  - 痛点二：效果评估全凭感觉，没有统一标准
    - 改完 Prompt，大家坐在一起人工看十几个例子，"我觉得这个回答更好"、"我觉得差不多"，没有量化指标，公说公有理婆说婆有理，决策效率低，而且人工抽查覆盖不了所有场景，很多边缘 case 根本测不到。
    - 新人改 Prompt 更是没有标准，不知道改成什么样算好，全靠摸索。
  - 痛点三：线上效果缓慢下降，发现不及时
    - 有一段时间用户点踩率慢慢上升，我们以为是正常波动，过了一周才发现是知识库更新引入了一批质量不好的文档，导致回答准确率下降，这期间已经影响了不少用户，非常被动。
    - 没有线上效果监控和基线，效果是慢慢变差的，就像温水煮青蛙，等发现的时候已经差了不少。
  - 痛点四：没有自动化，重复劳动多
    - 每次改 Prompt，都要人工找一堆测试问题，一个个跑，一个个看回答，一次优化要花大半天，效率极低，大家都不愿意做效果验证，能省则省，反而导致更多问题。
  - 这些问题的本质是：我们用传统软件工程的方法做 AI 应用，没有建立适配 AI 不确定性的质量保障体系，这是从 Demo 到产品必须跨过的坎。
3. 解决过程：从0到1搭建 Skill 自动化评测 Harness 和质量保障体系
  - 意识到问题的本质后，我们专门花了一个迭代的时间，集中解决这个问题，我作为核心开发负责整个评测体系的设计和实现，分几步走：
  - 第一步：调研和方案设计，明确评测体系的核心要素
    - 先调研了业界 AI 应用评测的做法，看了 LangChain 的评测模块、OpenAI 的 evals 框架，结合我们的业务场景，确定了评测体系的核心要素：
      1. 标准化的评测用例：每个 Skill 必须有覆盖各场景的测试用例，用例本身要版本化管理。
      2. 多层断言机制：适配 AI 输出的不确定性，不能只做精确匹配，要有结构化字段校验、关键词匹配、语义相似度、人工复核多种方式。
      3. 自动化执行工具：一条命令跑全量评测，自动生成报告，不用人工一个个跑。
      4. CI 质量门禁：评测接入流水线，变更必须通过评测才能合入，从流程上防止回归。
      5. 效果基线和漂移检测：线上建立效果基线，主动监控效果变化，不要等用户投诉。
    - 方案和团队对齐后，大家都认可这是解决问题的根本方向，不是临时补丁。
  - 第二步：定义 Skill 标准和评测用例规范
    - 先把 Skill 的输入输出 Schema 标准化，用 Pydantic 定义严格的输入输出模型，保证每个 Skill 的接口是规范的，这是自动化评测的基础——输入可构造，输出可校验。
    - 制定评测用例编写规范：
      - 每个 Skill 不少于 20 条用例，覆盖正常场景、边界 case、异常输入、高频问题四类。
      - 用例格式标准化：用例 ID、分类、输入、预期输出、断言配置、备注，存在 JSON 文件里，版本化管理。
      - 断言配置灵活：每条用例可以配置多种断言的组合，比如合同抽取用例用结构化字段校验（必须抽取合同方、金额、期限），法律问答用例用关键词匹配（必须包含"劳动合同法"、"仲裁时效"）+ 语义相似度。
    - 组织每个 Skill 的负责人，花了一周时间，把当时 8 个 Skill 的评测用例都补全了，总共 160 多条，形成了第一版质量基线，这是最花时间但也是最有价值的一步，因为评测质量取决于用例质量。
  - 第三步：开发自动化评测 Harness 工具
    - 用 Python + Pytest 开发了评测执行器，核心逻辑：
      1. 加载指定 Skill 的评测用例集，支持按 Skill、按分类筛选，支持增量评测（只跑变更影响的 Skill）。
      2. 每条用例调用 Skill 执行接口，传入输入，获取输出，有超时控制和异常捕获，单条失败不影响整体。
      3. 执行该用例配置的断言：结构化字段校验（用 Pydantic 解析输出，校验字段存在性、类型、值）、关键词包含/排除校验、语义相似度校验（用 Embedding 计算输出和预期的余弦相似度，超过阈值算通过），全部通过才算用例通过。
      4. 收集每条用例的结果（通过/失败、失败原因、输入输出快照、耗时），最后汇总生成评测报告。
    - 报告包含：整体通过率、各 Skill 通过率、失败用例详情（输入、预期、实际输出、哪个断言失败）、版本信息（Git Commit、数据集版本、Skill 版本），支持 JSON（机器可读）和 Markdown（人可读）两种格式。
    - 支持人工复核标记：机器难判断的用例标记为"待人工复核"，生成复核列表，人工确认后回填结果，不强行用机器判断。
    - 开发过程中踩了不少坑，比如语义相似度阈值怎么定（太高误杀正确答案，太低放过错误答案，我们反复调了几轮，根据不同 Skill 特性设不同阈值），比如流式输出的 Skill 怎么评测（要等流结束拿完整输出），都一一解决了。
  - 第四步：接入 CI 质量门禁，从流程上保障
    - 把评测 Harness 集成到 GitLab CI 流水线，在代码合并前执行，设计了三道门禁规则：
      1. 用例数量门禁：每个 Skill 评测用例不少于 20 条，新增 Skill 必须补全用例才能合入，防止有人不写用例。
      2. 通过率门禁：整体通过率不低于基线阈值（核心 Skill 95%，其他 90%），低于阈值不能合入。
      3. 回归门禁（最核心）：和主干分支的基线评测结果对比，任何之前通过的用例现在失败了（回归），直接阻塞合入，必须修复或走用例变更审批，这一条直接解决了"改好一个弄坏另一个"的痛点。
    - 评测报告自动评论到 MR 页面，评审者一眼就能看到本次变更的效果影响，通过率多少、有没有回归、哪些用例失败，评审有数据支撑，不再凭感觉。
    - 做了增量评测优化：普通 MR 只跑受影响的 Skill 评测，几分钟出结果，不影响开发节奏；每天夜间跑全量评测，更新质量基线；发布前必须跑全量，兼顾效率和质量。
  - 第五步：建立线上效果监控和漂移检测，形成闭环
    - 光有线下评测还不够，线上效果也要监控，我们做了：
      1. 建立线上效果基线：用稳定运行时的准确率、点踩率、转人工率作为基线。
      2. 每日抽样评测：每天自动抽样线上问答，用评估模型自动打分，统计准确率和幻觉率，和基线对比。
      3. 漂移告警：连续两天效果指标低于基线 5% 以上，触发告警，通知研发排查，自动分析可能原因（知识库更新、Prompt 变更、模型变化）。
      4. Bad case 自动收集：点踩、转人工、低置信度的回答自动进入 bad case 池，定期分析，补充到评测数据集，形成"线上发现问题 → 补充用例 → 优化 → 评测回归 → 上线"的闭环。
    - 这一步让我们从"被动等用户投诉"变成"主动发现问题"，效果下降能提前预警。
4. 最终效果和数据
  - 这套体系上线后，效果非常明显，有几个核心数据：
  - 回归问题基本杜绝：Prompt/Skill 变更导致的线上回归问题，从每月 3-4 起降到基本为零，所有回归都在 MR 阶段被门禁拦截了，大家改 Prompt 不再提心吊胆，敢大胆优化了，因为有全量评测兜底。
  - 迭代效率大幅提升：一次 Prompt 优化的效果验证，从人工跑大半天，变成自动化跑几分钟，而且覆盖全量场景，迭代速度提升了好几倍，项目后期 Skill 数量从 8 个增长到 16 个，评测用例从 160 条增长到 320 条，依然能保持高频迭代。
  - 回答质量稳步提升：有了量化评测和 bad case 闭环，法律问答的准确率从最开始的 80% 左右逐步提升到 90% 以上，幻觉率明显下降，用户点踩率降低了一半，质量提升有数据支撑，不再是凭感觉。
  - 线上问题发现提前：效果漂移检测上线后，成功提前发现了 2 次知识库更新导致的效果下降，在用户大规模投诉前就修复了，从被动变主动。
  - 团队认知提升：整个团队建立了"AI 应用质量靠工程化体系保障"的共识，不再觉得"AI 就是调 API，质量不可控"，大家都认可评测体系是 AI 应用的核心基础设施，新功能新 Skill 从一开始就会写评测用例，形成了文化。
5. 踩过的坑和经验教训
  - 这个过程不是一帆风顺的，也踩了不少坑：
  - **坑一：最开始断言设计得太严格，用精确字符串匹配，导致很多表述不同但意思对的答案被判失败，假失败很多，大家不信任评测结果，觉得"评测不准"。后来改成多层断言，结构化字段精确校验 + 关键词 + 语义相似度结合，减少假失败，评测结果可信度才提升，大家才愿意用。这让我深刻理解到 AI 评测不能追求非黑即白，要接受不确定性，设计合理的断言策略。
  - **坑二：最开始要求每次 MR 都跑全量评测，一次十几分钟，大家嫌慢，有抵触情绪，甚至有人想绕过门禁。后来做了增量评测，普通 MR 只跑受影响的 Skill，几分钟出结果，夜间跑全量，大家就接受了，效率和质量兼顾。这让我意识到好的工程工具也要考虑用户体验，不能为了质量牺牲太多效率，否则大家会用脚投票。
  - **坑三：评测用例质量参差不齐，最开始有人随便写几条用例凑数，导致评测覆盖度不够，还是有线上问题。后来制定了用例规范，要求覆盖四类场景，并且用例走评审，同时把线上 bad case 持续补充进来，用例质量才提上来。这让我意识到评测体系的上限取决于用例质量，工具只是基础，高质量的测试数据集才是核心资产，需要持续投入建设。
  - **坑四：最开始只做线下评测，没做线上监控，有一次线下评测都通过了，但线上用户提问分布变化了，效果还是下降了。后来加上线上抽样评测和漂移检测，线下线上结合，才形成完整的质量保障。这让我意识到线下评测覆盖的是已知场景，线上还有未知分布，必须线上监控兜底。
6. 最大的收获和思考
  - 这个挑战的解决，是我做这个项目最大的成长，收获不只是做了一个工具，而是建立了对 AI 应用工程化的体系化认知：
  - 收获一：深刻理解了 AI 应用和传统应用的本质区别
    - 传统应用的核心是确定性逻辑，质量保障靠功能测试；AI 应用的核心是不确定性的模型输出，质量保障必须靠专门的评测体系、效果监控、数据闭环，这是完全不同的方法论，不能用传统软件工程的思路硬套。
    - 以前觉得 AI 应用就是"调 API + 写 Prompt"，做完这个项目才明白，从 Demo 到生产级产品，中间隔着一整套工程化体系，评测、降级、成本管控、效果监控，这些"不性感"的工程工作才是 AI 真正能稳定服务用户的核心，也是工程师的核心价值所在。
  - 收获二：学会了从本质问题出发，体系化解决问题，而不是打补丁
    - 最开始遇到回归问题，我们的第一反应是"改完 Prompt 多测几个场景"，是打补丁的思路，解决不了根本问题。后来停下来思考本质：AI 输出不确定，传统测试不适用，需要建立适配的质量体系，然后从用例规范、断言机制、自动化工具、CI 门禁、线上监控全链路体系化解决，才真正解决了问题。
    - 这让我养成了遇到问题先想本质、再设计体系化方案的思维，而不是头痛医头脚痛医脚。
  - 收获三：体会到了工具和流程对团队效率的放大作用
    - 一个好的工程工具和流程，能把团队从重复劳动中解放出来，让大家敢大胆创新，因为有兜底。评测体系上线后，团队的迭代速度和质量都提升了，这不是某个人能力强能做到的，而是工具和流程的力量。
    - 也让我意识到，做平台型工具，要考虑使用者的体验，效率和质量要平衡，否则再好的工具大家也不愿意用，推行不下去的工具就没有价值。
  - 收获四：数据驱动的思维方式
    - 以前做优化可能凭感觉"我觉得变好了"，现在做任何优化都要有数据支撑，效果提升多少、成本降低多少、有没有回归，用评测数据说话，决策更理性，也更有说服力。
    - 这种数据驱动的思维不仅适用于 AI 项目，也适用于所有技术工作，用数据量化价值，比空泛的描述有力得多。
  - 收获五：对技术价值的重新理解
    - 这个挑战不是什么高难度的算法，也不是什么酷炫的新技术，而是一个工程化体系的建设，但它给项目带来的价值是巨大的——质量提升、迭代加速、成本降低、用户满意度提升。这让我明白，工程师的价值不在于用了多牛的技术，而在于能不能解决真实的业务痛点，用合适的技术创造实际的价值，工程化能力在 AI 时代不仅没有过时，反而更加重要，因为 AI 的不确定性更需要严谨的工程体系来兜底。
  - 这个项目之后，我更加确定自己要在 AI 工程化这个方向深耕，把 AI 能力做成稳定、可靠、低成本、可迭代的生产级产品，这是一个很有挑战也很有价值的方向，也是我接下来继续成长的目标。
