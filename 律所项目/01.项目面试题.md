# 简单介绍你的项目
面向律所客服,合同审查,律师办案和销售质检这几个场景搭建的基于python和go开发的rag项目,实现了法律问答,合同风险识别,通话质检,客户打标,案件辅助等能力
技术栈: Python、FastAPI、LangGraph、MCP、RAG、DeepSeek API、Embedding、NumPy、Prompt Engineering、ASR、MySQL、Go、Gin、GORM、Docker Compose、Pytest、Go Test、CI/CD、模型调用审计与 Token 成本统计

### 核心工作:
* 负责法律问答rag建设. deepseek embedding对法律FAQ(常见问题解答Frequently Asked Questions)进行向量化,通过余弦相似度完成对前top-k条相关的文档进行召回,并设计"远程知识库->本地向量库->关键词匹配的多级降级机制,提高系统在外部服务异常时的可用性(知识量排序:远程知识库>>本地向量库>>关键词匹配. 远程知识库挂了或者没回答上来,用本地向量库,本地向量库没回答上来,用关键词匹配)
* 参与skill能力构建,按照`输入schema,执行逻辑,输出schema,版本信息封装法律问答,合同抽取,风险审查,客户打标,销售质检`等能力封装skill,让agent按需组合调用
* 实现skill自动化评测harness,支持关键词匹配,结构化字段校验,人工复核标记,自动生成包含git commit,数据集版本,skill版本,失败样例的评测报告(skill去评测,并生成评测报告)
* 将评测流程接入CI质量门禁,评测用例数量不足或断言失败时返回非零状态,组织质量退化的不合格代码合入,推动prompt调优从人工抽查变成自动化
* 基于langgraph实现多轮咨询agent,完成会话状态管理,知识检索,答案生成,客户意向识别,跟进记录生成等Node节点编排
* 参与销售通话质检模块开发,封装云端asr,本地whisper,阿里云funasr,双声道转写能力,实现声音转文字,结合规则匹配输出合规风险,用户意向和跟进建议
* 实现llm调用token统计和费用估算,区分输入token,输出token,embedding用量.单价和估算费用写入记录以便成本分析和模型选型
* 参与go harness运行时治理(runtime壳),完成超时/网络错误分类,指数退避重试,熔断状态机,上下文隔离,人工接管队列,加强agent调用链路异常恢复能力

### 整体架构和为什么go+python选型
项目定位:
    给律所用的b端项目(b端是去客户公司给他们单独部署使用,例如公司内部的打卡系统,只给该公司用,c端是提供一个服务给全球互联网用户使用,例如抖音),功能上覆盖客服咨询,合同审查,律师办案,销售质检,内容生产(什么内容?)
目标: 
    提升律所效率,降低人工成本.之前客服成本很高,合规审查工作量很大
分层架构:
    接入层: go+gin组成的api网关(鉴权,限流,路由转发,接收外部请求)
    AI能力层:python+fastapi(rag检索,agent编排,skill执行,asr转写)
    数据层:mysql存储业务数据和审计数据,向量数据库存储法律知识转换的embedding,redis做缓存和会话状态管理
    工程化层: k8s编排服务,pytest+go test测试代码,CICD集成质量门禁
go+python选型理由:
    python负责ai逻辑层:langgraph,langchain,embedding,asr python中支持成熟,效率高
    go负责工程底座:gin性能高,适合做网关以及harness运行时治理,工具执行等稳定性和性能要求高的模块,gorm做数据访问
    通信方式:go->gRpc->python,接口契约先行
优势:
    python快速试错,go保障服务高可用.故障隔离,ai服务异常不影响网关和网站,降级机制保障服务可用

### Skill能力体系怎么设计,为什么skill抽象而不是写死代码
skill定义:
    skill是对ai能力的标准化封装,每个skill对应一个独立业务能力(法律问答,合同抽取,风险审查,客户打标,销售质检)
    本质是把复杂ai逻辑(prompt+tool调用+后续处理)封装成标准化可复用可评测可版本公里的能力组件,让agent按需调用
skill封装四要素:
1. 输入schema:用json schema严格定义入参(参数名,类型,是否必填,枚举值,格式约束,自然语言描述description,告诉模型参数含义和应该传什么)
2. 执行逻辑:skill核心业务代码,prompt模板渲染,llm调用,工具调用,结果后续处理,异常处理.全部封装在执行函数里
3. 输出schema:json schema定义返回结果格式,保证输出可解析可校验可被下游skill或agent消费,避免自由输出导致混乱
4. 版本信息:每个skill有独立版本号和变更记录,支持灰度发布和回滚,配合评测报告追溯每个版本质量变化

Skill抽象核心价值:
1. 复用性:通用能力一次开发多个agent调用,法律问答skill在客服场景和办案场景都能用
2. 可评测性:标准化输入输出让自动化测评可能,每个skill都能被独立写测试用力,跑断言,出测评报告,建立质量基线
3. 可维护性:修改一个skill不影响其他能力,出问题快速定位具体skill和版本
4. 可组合性:agent随意组合多个skill完成复杂任务(客户咨询-法律问答-客户打标-跟进记录生成 四个skill串联)
5. 团队协作:不同人负责不同skill,并行开发,通过schema约定接口

落地效果:
1. 16个skil配合自动化测评harness,质量可量化,prompt调优有数据支撑

### Ai在项目落地最大挑战
1. 法律专业度要求高,幻觉代价大: 准确性要求极高,答错一个法条或合同风险点,需要律所承担法律责任,容易被告

应对: 
* 搭建法律专属rag,所有答案必须基于法律FAQ和法条原文,prompt严格遵守无依据不回答
* 建立skill自动化测评体系,每个法律skill不少于20条测评用例,覆盖边界case,prompt变更需要通过测评门禁
* 高风险场景(合同审查,法律意见)保留人工复核环节,ai辅助建议,律师确认结论

2. 业务流程复杂,ai难以标准化: 合同审查,办案流程,销售质检每个团队习惯不一样,难以一套流程覆盖,定制成本高

应对:
* skill化抽象,把通用能力(合同条款抽取,风险点识别,通话转写)标准化
* 每个skill支持配置化,比如黑瞳审查的风险阈值,质检的规则库,可以按律所要求调整,不改代码

3. 数据安全和合规要求高:客户信息,合同内容,案件材料都是高度敏感信息

应对:
* 建立llm审计机制,每次模型调用都记录输入输出,token用量,费用,全链路追溯
* 设计多级降级机制,外部embedding服务异常时自动降级到本地向量库和关键词匹配,保障可用性,减少敏感数据外传
* 客户数据,黑瞳内容脱敏处理后进ai流程,敏感字段不落库到日志

4. ai效果难量化,价值无法证明

应对:
* token成本核算机制,每次调用都有费用记录,做成本计算
* 质检,合同审查场景做效率对比,人工审查和ai辅助后的变化
* 评测报告量化skill准确率和通过率,让质量可衡量

### rag专项
### rag链路具体实现,为什么用余弦相似度做top-k返回
1. 法律问答rag全链路实现
第一步:知识库构建
   * 收集法律FAQ,法条原文、律所常见问题解答等文档,清洗去重，去掉页眉页脚、无关模板内容
   * 按法律条文的自然结构做语义切片，比如一条法条、一个 FAQ 问答对作为一个 Chunk，保证语义完整
   * 调用 DeepSeek Embedding 模型，把每个 Chunk 转成向量，存入本地向量库（基于 NumPy 实现的轻量向量存储），同时保存原文和元数据（法条编号、分类、更新时间）
第二步: 查询召回
   * 用户提问进来先预处理,去掉无关语气词,提取核心法律问题
   * 用同一个embedding模型把用户问题转成查询向量
   * 计算查询向量和知识库中所有向量的余弦相似度,相似度排序后取top-k(3-5条)作为召回结果
   * 对召回结果最高相似度低于阈值的,判定为知识库无相关内容,走兜底逻辑,不强行回答
第三步: 答案生成
   * 把召回的法律条文和FAQ原文作为上下文,拼入prompt,要求llm'只能基于提供的参考资料回答,参考资料没有的就说无法解答'
   * 调用deepseek生成答案,答案标注引用来源(法条或FAQ),增强可信度
   * 生成后做简单后续处理,见擦汗是否有明显幻觉内容,格式化为用户易读形式
2. 为什么用余弦相似度做召回
   *  原理适配:余弦相似度是两个向量在方向上的相似程度,适合文本语义适配语义相近的句子,长度不同向量方向也会接近
   *  计算高效:计算复杂度低,几万条法律知识也能毫秒级完成计算.否则得引入向量数据库
   * 效果验证:法律FAQ场景下,余弦相似度相关问题相似度高,不相关问题普遍在0.6以下,容易区分
   * 轻量可降级: 不依赖外部服务,是多级降级机制的基础,外部embedding挂了本地向量库(余弦相似)还能工作
3. 法律场景优化
   4. 法律术语多,通用embedding对专业术语表征不够准,prompt层做了补偿,要求模型有限匹配法条编号和专业术语
   5. 对高频问题缓存,相似度高的问题直接返回历史答案

### 远程知识库->本地向量库->关键词匹配 多级降级机制具体实现,解决什么问题
1. 为什么需要多级降级
    * rag依赖deepseek的embedding服务和远程知识库,外部服务出现故障没兜底容易让法律问答功能瘫痪
    * 本地开发环境没有外部embedding服务访问权限,开发同学无法在本地电脑上自测功能
哪三级:
1. 第一级:远程知识库(正常模式) 外部embedding服务和远程知识库正常时用
   实现步骤:
   * 用户提问调用deepseek embedding接口生成查询向量
   * 远程向量知识库中做相似度检索,召回top-k结果
   * 远程知识库数据最新最多,embedding模型召回准确率高
当远程接口超时或返回错误码,降级到下一级

2. 第二级:本地向量库(半降级模式)
   实现步骤:
    * 定期把远程知识库的FAQ同步到本地,用embedding模型预先计算好向量,存入本地文件或轻量数据库
    * 远程服务挂后自动切换到本地想来个内裤,用户提问用本地缓存的embedding能力做余弦相似度检索
    * 本地向量库数据不一定最新,但核心法律条纹都在
价值:外部数据库不可用,问答任然能用

3. 第三级: 关键词匹配(兜底模式) 本地向量不可用,本地没有embedding模型
   实现步骤:
   * 关键词匹配,对用户提问做分词,提取核心关键词,和法律条纹标题,标签进行关键词匹配,按匹配排序返回最相关的几条(提问杀人判几年,用杀人去搜索杀人相关的法律条文)
   * 匹配算法用TF-IDF或者关键词命中数量排序,纯py无依赖
价值: 最终兜底,无需外部依赖,不会挂

工程中需要做什么:
    自动切换: 健康检查外部服务,自动切换下一级
    状态标记: 降级状态记录到日志和监控,告警通知运维及时排查
    统一接口: 上层业务代码统一调用,三级召回统一对外暴露

### 你们设计的rag和通用rag区别,做了什么优化
1. 准确性要求高,幻觉代价大,有法律风险
    优化:
        1. prompt层强约束,要求:必须基于参考资料回答，无依据直接说无法解答，禁止推测
        2. 召回侧设置阈值,阈值不够不回答
        3. 高风险问题自动提示:AI 仅供参考，建议咨询专业律师
2. 专业术语多，语义匹配难度大
   优化:
        1. 切片保留法条完整,不切开
        2. 召回后增加关键词校验,用户问盗窃罪,召回内容必须包含盗窃罪,不然降低权重
        3. 建立法律术语同义词词典,离婚->接触婚姻关系做映射,提高召回率
3. 知识结构规整,时效性要求高: 法条修订、司法解释更新后旧内容就失效了，不能用旧法条回答
   优化
        1. 每个知识带生效时间,失效时间
        2. 知识库版本管理,法条更新后旧版本失效
        3. 答案中标注法条生效时间
4. 答案严谨可追溯: 通用场景答案口语化、灵活就行；法律场景答案必须严谨、有依据、可追溯
   优化
        1. 让大模型结构化输出答案,'结论 + 法律依据 + 参考法条编号'
        2. 每个结论对应召回原文片段支持查看原文
        3. 后续处理校验答案中法条编号是否存在于召回内容中,没出现的删掉,防止编造
5. 用户提问模糊,需要引导澄清  法律场景用户经常描述不清，比如"我被打了怎么办"，不同情况（伤情、原因、地点）适用法律完全不同
    优化
        1. 增加意图识别和澄清节点,信息不足时agent不直接回答,而是反问用户关键信息
        2. 进行分类引导,用户先选大类(婚姻,劳动,刑事),细化问题,提升匹配度
